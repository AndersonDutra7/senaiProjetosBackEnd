Panorama do Desenvolvimento Back-End

Compreendendo o ciclo de vida do software, comunicação assertiva, resolução científica de problemas e relações institucionais na engenharia de sistemas.

⏱️ Duração: 3 horas (Presencial)
🎯 Foco: Fundamentos, Soft Skills & Prática Dev
🚀 Módulo: Desenvolvimento Back-End
01

O Papel do Desenvolvedor Back-End no Ciclo de Vida do Sistema Web

⏱️ Duração Estimada: 45 min

O desenvolvedor Back-End é o engenheiro responsável por tudo aquilo que o usuário não vê diretamente, mas que viabiliza toda a operação da aplicação: regras de negócio, segurança, integração com banco de dados, autenticação e desempenho.

🖥️ 1. Análise & Arquitetura

Tradução de requisitos de negócio em esquemas de banco de dados, diagramas de fluxo de dados e escolha da pilha de tecnologia (Node.js, Python, Java, etc.).

🔌 2. Construção de APIs

Criação dos caminhos de comunicação (REST, GraphQL) que permitem ao Front-End ou aplicativos móveis enviarem e receberem informações de forma segura.

💾 3. Gestão de Dados

Modelagem relacional/não-relacional, escrita de queries otimizadas, garantia de transações seguras e prevenção contra corrupção de dados.

🛡️ 4. Segurança & Deploy

Proteção contra vulnerabilidades (SQL Injection, XSS), gerenciamento de credenciais (variáveis de ambiente) e publicação do sistema em nuvem.

💡 Visão de Processo: O ciclo de vida de uma requisição típica envolve: Cliente (Front-End) ➔ Requisição HTTP ➔ Servidor Web (Back-End) ➔ Validação & Regra de Negócio ➔ Banco de Dados ➔ Resposta HTTP (JSON).
02

Comunicação Não Violenta (CNV) nos Ambientes de Trabalho

⏱️ Duração Estimada: 45 min

Projetos de software modernos são construídos por equipes, não por desenvolvedores isolados. A Comunicação Não Violenta (CNV), estruturada por Marshall Rosenberg, é uma ferramenta essencial para revisão de código (Code Reviews), alinhamento técnico e resolução de incidentes sem gerar atritos tóxicos.

1

Observação sem Julgamento

Descreva os fatos objetivos. Em vez de "Seu código está horrível", use "Percebi que esta consulta SQL não utiliza índices e consome muita memória".

2

Sentimento / Impacto Técnico

Expresse a preocupação de forma profissional. Exemplo: "Fico preocupado com a estabilidade do sistema quando entrarmos em produção sob alta carga."

3

Necessidade

Identifique o valor do projeto a ser atendido. Exemplo: "Precisamos manter o tempo de resposta da API abaixo de 200ms para atender aos requisitos de SLA."

4

Pedido Concreto

Faça uma solicitação clara e executável. Exemplo: "Podemos refatorar essa função aplicando paginação antes de aprovar este Pull Request?"

Exemplos Práticos em Code Reviews:

❌ Comunicação Reativa / Violenta

"Você esqueceu de tratar os erros de novo! Assim o servidor vai cair toda hora. Corrige isso aí."

✅ Aplicação de CNV

"Notei que o bloco try/catch não está tratando exceções na rota de pagamentos. Preocupo-me com a experiência do usuário se o banco falhar. Consegue adicionar um tratamento de erro estruturado?"

🤝 Cultura de "Blameless Post-Mortem": Quando ocorre um bug em produção, o foco da equipe nunca deve ser "quem errou?", mas sim "qual falha no nosso processo ou teste permitiu que esse bug chegasse até aqui?".
03

Resolução de Problemas: Método Científico no Dia a Dia Dev

⏱️ Duração Estimada: 45 min

Junior e Senior devs não se diferenciam pela ausência de erros, mas pela metodologia utilizada para investigar e resolver bugs. Debugar não é adivinhar ou alterar código aleatoriamente até funcionar.

A

1. Reprodução do Problema & Coleta de Dados

Isole o erro. Obtenha logs, códigos de status HTTP, dados de entrada e passos exatos para reproduzir o problema no ambiente local.

B

2. Proposição de Hipóteses

Com base nos logs, crie teorias testáveis. "Hipótese A: O token JWT está expirando antes do tempo." / "Hipótese B: O banco de dados está rejeitando campos nulos."

C

3. Testagem Controlada (Isolamento de Variáveis)

Modifique apenas uma variável por vez. Utilize breakpoints, logs direcionados ou testes unitários para validar ou descartar cada hipótese de forma isolada.

D

4. Validação & Solução Definitiva

Após confirmar a causa raiz, implemente a correção, rode a bateria de testes e certifique-se de que a alteração não gerou efeitos colaterais (bugs de regressão).

🐤 Técnica do Pato de Borracha (Rubber Duck Debugging): Explicar o código linha por linha, em voz alta, para um objeto inanimado (ou colega de equipe) força o cérebro a desacelerar e frequentemente revela a falha lógica antes mesmo de terminar a explicação.
04

Relações Institucionais em Projetos de Software

⏱️ Duração Estimada: 45 min

O software nunca existe no vácuo. O desenvolvedor Back-End interage constantemente com diferentes perfis profissionais (stakeholders), cada um com suas próprias linguagens e expectativas.

👥 Clientes Internos

Designers / UI-UX: Alinhamento sobre quais dados o Back-End pode fornecer em tempo real.
QA / Pessoas de Teste: Fornecimento de dados de teste, mocks e ambientes estáveis.
Tech Lead / Arquitetos: Seguir padrões de código e decisões de arquitetura da empresa.

🏢 Clientes Externos & Negócio

Product Owners (PO) / Stakeholders: Traduzir necessidades de negócio em funcionalidades viáveis.
Clientes Finais: Garantir que as regras do sistema atendam às dores reais de quem usa a plataforma.

🌱 Liderança & Pares

Devs Juniores / Estagiários: Apoiar com mentoria, documentação clara e pareamento.
Devs Seniores / Gestores: Transparência sobre prazos, riscos técnicos e impedimentos.

⚖️ Gestão de Trade-Offs (Compromissos): Um bom desenvolvedor Back-End sabe explicar para a área de negócios o impacto de decisões técnicas. Se o cliente quer uma nova funcionalidade entregue com urgência, cabe ao dev apresentar as opções: aumentar o custo, reduzir o escopo ou aceitar um débito técnico planejado.
🛠️ Atividade Prática Integrada — Estudo de Caso (Em Grupos)

Cenário: Em um e-commerce de grande porte na véspera da Black Friday, o serviço de pagamentos Back-End começou a apresentar oscilações e falhas intermittentemente. A equipe de suporte está pressionada, o Product Owner exige uma solução imediata e os desenvolvedores Front e Back estão trocando acusações sobre de quem é a culpa.

Desafio dos Grupos:

  1. Aplicação de CNV: Escreva como o Tech Lead deve abordar a equipe para conter a crise sem buscar culpados.
  2. Resolução de Problemas: Formule 2 hipóteses técnicas para o problema (ex: timeout de banco, estouro de conexões) e descreva os passos para testá-las.
  3. Relação Institucional: Prepare uma mensagem sucinta e profissional para o Product Owner informando o status da crise e a previsão de estabilização.
