01

Técnicas de Levantamento de Requisitos e Demandas do Cliente

⏱️ Duração Estimada: 60 min

Um dos maiores motivos de falha em projetos de software não é o código ruim, mas a falta de clareza sobre o que deveria ser construído. O levantamento (elicitação) de requisitos conecta a necessidade de negócio do cliente com o desenvolvimento técnico do Back-End.

1. Requisitos Funcionais vs. Não-Funcionais

Tipo de Requisito Definição Didática Exemplo Prático (Visão Back-End)
Requisitos Funcionais (RF) O que o sistema deve fazer. Descreve as ações, rotas, regras de negócio e saídas esperadas. RF01: O sistema deve permitir o cadastro de clientes com validação de CPF único.
Requisitos Não-Funcionais (RNF) Como o sistema deve se comportar. Define restrições de desempenho, segurança, escala e disponibilidade. RNF01: A API de autenticação deve responder em menos de 200ms sob carga de 1000 requisições simultâneas.

2. Escrevendo User Stories (Histórias de Usuário)

No desenvolvimento ágil, requisitos funcionais são expressos no formato de User Stories para manter o foco no valor entregue ao usuário:

Template de User Story:
Como [Papel do Usuário], eu quero [Funcionalidade/Ação], para que [Objetivo/Benefício de Negócio].

3. Critérios de Aceite (Definition of Done)

Cada User Story deve conter Critérios de Aceite testáveis para que o dev saiba exatamente quando a tarefa está concluída:

📝 Exemplo Completo de User Story Back-End:

História: "Como cliente da loja, quero redefinir minha senha via e-mail para que eu possa recuperar o acesso à minha conta caso a esqueça."

Critérios de Aceite Técnicos:

  • Deve ser gerado um token criptográfico temporário válido por 15 minutos.
  • A API deve retornar HTTP status 200 OK com mensagem padrão, sem revelar se o e-mail existe no banco (prevenção contra enunciação de usuários).
  • A nova senha deve possuir no mínimo 8 caracteres, contendo letras e números (hash em bcrypt).
02

Metodologias Ágeis: Princípios, Priorização MoSCoW e Kanban

⏱️ Duração Estimada: 60 min

As Metodologias Ágeis valorizam entregas incrementais contínuas, feedback rápido e adaptação a mudanças em vez de planejamentos rígidos e extensos.

1. Priorização com o Método MoSCoW

Nem todas as demandas possuem a mesma relevância. A matriz MoSCoW ajuda a definir o escopo do MVP (Produto Mínimo Viável):

MUST HAVE Indispensável

Sem esta funcionalidade o sistema não funciona ou perde o sentido comercial. Ex: Autenticação e persistência de dados essenciais.

SHOULD HAVE Importante

Funcionalidade de alto valor que deve ser incluída se houver tempo, mas que não impede o lançamento do MVP. Ex: Envio de e-mail de confirmação.

COULD HAVE Desejável

Pequenas melhorias de experiência ou extras que só serão feitos se o cronograma estiver adiantado. Ex: Tema escuro configurável na API.

WON'T HAVE Fora do Escopo

Funcionalidades combinadas que não serão desenvolvidas nesta versão/sprint. Evita o aumento descontrolado do escopo (Scope Creep).

2. Gestão Visual com Quadro Kanban

O Kanban utiliza colunas visuais e o princípio de limite de WIP (Work In Progress) para garantir um fluxo contínuo de entregas sem sobrecarregar os desenvolvedores.

03

Desenvolvimento de Projetos: Organização de Sprints e Etapas

⏱️ Duração Estimada: 60 min

Para organizar o projeto prático do curso, dividiremos o desenvolvimento em Sprints (ciclos de entrega contínua). Cada Sprint possui um objetivo claro e termina com um software funcional testado.

1

Sprint Planning (Planejamento)

A equipe seleciona as User Stories do Product Backlog com maior prioridade (MoSCoW) e as decompõe em tarefas técnicas executáveis de Back-End (ex: criar tabela no banco, escrever rota do controller, validar campos).

2

Execução & Dailies (Reuniões Diárias)

Desenvolvimento focado nas tarefas da Sprint. Alinhamentos rápidos de 15 minutos respondendo a três perguntas: O que fiz ontem? O que farei hoje? Há algum impedimento técnico no meu caminho?

3

Sprint Review & Retrospectiva

Demonstração das rotas e funcionalidades construídas para validação do cliente/professor e reunião interna da equipe para responder: O que funcionou bem? O que podemos melhorar na próxima Sprint?

Exemplo de Decomposição: De User Story a Tarefas Técnicas Back-End

User Story: "Cadastro de Produtos no Sistema"

Task 1 (Banco): Criar migration SQL da tabela produtos com FK de categoria.
Task 2 (Model): Escrever ProdutoModel com método de inserção e busca.
Task 3 (Controller): Criar POST /produtos com validação de campos obrigatórios.
🛠️ Atividade Prática Integrada — Planejamento da Sprint 1 do Projeto (Em Equipe)

Cenário: Cada equipe/dupla iniciará o planejamento do projeto prático do curso (módulo Back-End). Vocês devem definir os requisitos iniciais, priorizá-los e preparar o Backlog da primeira Sprint.

Roteiro do Exercício Prático:

  1. Elicitação de Requisitos: Liste no mínimo 3 Requisitos Funcionais (RF) e 2 Requisitos Não-Funcionais (RNF) do sistema escolhido.
  2. Escrita de User Stories: Escolha 2 Requisitos Funcionais e transforme-os no formato padronizado de User Story contendo 3 Critérios de Aceite técnicos cada.
  3. Classificação MoSCoW: Classifique todos os requisitos em Must Have, Should Have, Could Have ou Won't Have.
  4. Montagem do Backlog da Sprint 1: Selecione os itens Must Have e decomponha-os em tarefas técnicas de Back-End (Banco de Dados, Models, Controllers e Rotas) organizando-as nas colunas do seu quadro Kanban.
