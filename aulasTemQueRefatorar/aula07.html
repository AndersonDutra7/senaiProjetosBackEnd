01

Modelagem de Dados: Entidades, Atributos e Relacionamentos (MER)

⏱️ Duração Estimada: 60 min

A Modelagem Conceitual é a primeira fase do projeto de banco de dados relacional. O objetivo é criar o **Modelo Entidade-Relacionamento (MER)**, representando abstratamente os elementos do negócio do mundo real independentemente do SGBD que será utilizado.

🏢 1. Entidades (Forte vs. Fraca)

Entidade: Conjunto de objetos do mundo real sobre os quais precisamos guardar dados.
• Entidade Forte: Existe de forma autônoma. Ex: Cliente_B2B, Produto.
• Entidade Fraca: Depende da existência de outra entidade pai. Ex: Item_Pedido (só existe vinculada a um Pedido).

🏷️ 2. Atributos e Suas Categoriais

Propriedades que descrevem uma entidade.
• Atributo Simples (Atômico): Inseparável (ex: CNPJ, Preco).
• Atributo Composto: Subdividido (ex: Endereco ➔ Logradouro, Número, CEP).
• Atributo Derivado: Calculado a partir de outros (ex: Valor_Total = Qtd * Preco_Unitario).

🔗 3. Relacionamentos

Associações lógicas entre duas ou mais entidades que expressam as regras do negócio.
Exemplo: "Cliente B2B REALIZA Pedido" / "Pedido CONTÉM Itens de Pedido".

📊 4. Mapeamento de Cardinalidades

Define o número mínimo e máximo de ocorrências de uma entidade associada a outra:
• 1:1 (Um para Um): Ex: Usuário e Perfil de Acesso.
• 1:N (Um para Muitos): Ex: Um Cliente B2B realiza N Pedidos.
• N:M (Muitos para Muitos): Ex: Pedidos e Produtos (gera tabela associativa).

Exemplo Prático de Cardinalidades no Domínio B2B:

Entidade Origem Relacionamento Entidade Destino Cardinalidade (Mín:Máx) Regra de Negócio Traduzida
Cliente_B2B Realiza Pedido 1:N (0,n) Um cliente B2B pode cadastrar-se sem compras (0) ou realizar múltiplos pedidos (N). Todo pedido pertence a exatamente 1 cliente.
Pedido Contém Item_Pedido 1:N (1,n) Um pedido precisa conter no mínimo 1 item (1) e pode ter vários (N). Cada item pertence obrigatoriamente a 1 pedido.
Produto Possui Inventario 1:1 (1,1) Cada produto cadastrado possui exatamente 1 registro de saldo no estoque de inventário industrial.
💡 Dica de Modelagem: Relacionamentos do tipo N:M (Muitos para Muitos) não podem ser implementados diretamente no banco relacional. Eles devem ser transformados em uma Tabela Associativa/Intermediária contendo as Chaves Estrangeiras das duas entidades originais (ex: `Pedido_Produto` ou `Item_Pedido`).
02

Chaves Primárias e Estrangeiras: Garantindo Integridade Referencial

⏱️ Duração Estimada: 60 min

Em um banco de dados relacional, as chaves garantem a unicidade dos registros e a rastreabilidade das conexões entre tabelas. A Integridade Referencial impede que existam "dados órfãos" no sistema (por exemplo, um pedido associado a um cliente que não existe).

🔑 Chave Primária (Primary Key - PK)

Identificador único de cada linha em uma tabela.
• Deve ser obrigatoriamente ÚNICA e NOT NULL.
• Surrogate Key (Chave Substituta): Identificador sintético numérico ou UUID gerado pelo banco (Ex: BIGSERIAL, UUID). Prática recomendada!
• Natural Key: Dado do mundo real (Ex: CNPJ). Evitado como PK por poder sofrer alterações cadastrais.

🗝️ Chave Estrangeira (Foreign Key - FK)

Coluna em uma tabela que faz referência direta à Chave Primária (PK) de outra tabela.
• Estabelece o vínculo relacional entre os dados.
• O banco de dados rejeita qualquer inserção na tabela filha cuja FK não corresponda a um valor existente na tabela pai.

Ações de Constraint em Foreign Keys (Comportamento em Exclusão/Atualização)

1

ON DELETE RESTRICT / NO ACTION (Padrão e Recomendado para Finanças/Pedidos)

Impede a exclusão de um registro pai enquanto houver registros filhos vinculados. Ex: Bloqueia a exclusão de um `Cliente_B2B` caso existam `Pedidos` históricos cadastrados para ele.

2

ON DELETE CASCADE

Exclui automaticamente todos os registros filhos caso o pai seja deletado. Ex: Se um `Pedido` for excluído, todos os seus `Itens_Pedido` associados são apagados automaticamente.

3

ON DELETE SET NULL

Preserva os registros filhos, atribuindo valor `NULL` na coluna da FK quando o registro pai for excluído.

Exemplo de DDL com Constraints Nomeadas em PostgreSQL:

-- Tabela Pai (Clientes B2B)
CREATE TABLE clientes_b2b (
    id_cliente BIGSERIAL,
    razao_social VARCHAR(150) NOT NULL,
    cnpj VARCHAR(14) NOT NULL,
    
    CONSTRAINT pk_clientes_b2b PRIMARY KEY (id_cliente),
    CONSTRAINT uq_clientes_b2b_cnpj UNIQUE (cnpj)
);

-- Tabela Filha (Pedidos B2B)
CREATE TABLE pedidos (
    id_pedido BIGSERIAL,
    id_cliente BIGINT NOT NULL,
    data_pedido TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    status_pedido VARCHAR(30) DEFAULT 'RASCUNHO',
    
    CONSTRAINT pk_pedidos PRIMARY KEY (id_pedido),
    CONSTRAINT fk_pedidos_cliente FOREIGN KEY (id_cliente)
        REFERENCES clientes_b2b (id_cliente)
        ON DELETE RESTRICT
        ON UPDATE CASCADE
);
✨ Padronização de Nomes de Constraints: Nomeie explicitamente todas as restrições no script DDL. Utilize prefixos claros: pk_tabela para Primary Keys, fk_origem_destino para Foreign Keys e uq_tabela_campo para restrições Unique.
03

Levantamento de Requisitos de Armazenamento de Dados do Projeto

⏱️ Duração Estimada: 60 min

O levantamento de requisitos de armazenamento determina quais informações a aplicação Back-End precisa guardar, o tipo de dado nativo mais eficiente para cada campo e as estratégias de retenção para garantir o funcionamento do banco sob alta carga.

1. Tipos de Dados Nativos no PostgreSQL e Casos de Uso

Categoria de Dado Tipo Nativo PostgreSQL Caso de Uso Recomendado no Portal B2B
Identificadores (PK/FK) BIGSERIAL / UUID Chaves primárias de autoincremento para grandes volumes ou UUID para APIs expostas.
Textos Curtos / Códigos VARCHAR(N) / CHAR(N) VARCHAR(14) para CNPJ sem formatação; VARCHAR(100) para nomes/e-mails.
Valores Monetários NUMERIC(12,2) ou DECIMAL Preços de produtos e totais de pedidos. NUNCA use FLOAT/DOUBLE para dinheiro!
Datas e Horários TIMESTAMP WITH TIME ZONE Data/hora exata de criação de pedidos e atualizações com suporte a fusos horários.
Dados Flexíveis / Mocks JSONB Logs de integração com a logística industrial ou metadados de auditoria.

2. Historização e Imutabilidade de Preços

⚠️ O Problema da Alteração de Preço de Produtos:

Se a tabela Item_Pedido mantivesse apenas a referência (`id_produto`) sem salvar o valor no momento da venda, alterar o preço do produto na tabela Produtos modificaria retroativamente o valor de todos os pedidos históricos da empresa!

✅ A Solução de Arquitetura:

A tabela de junção Item_Pedido DEVE possuir uma coluna própria `preco_unitario_momento DECIMAL(12,2)` que armazena uma cópia congelada do preço no exato instante em que a compra foi confirmada.
