Boas Práticas de Segurança e Tratamento de Dados no Banco de Dados

⏱️ Duração Estimada: 60 min

A segurança em bancos de dados relacionais envolve duas frentes críticas: o **Gerenciamento de Acessos e Permissões (RBAC - Role-Based Access Control)** e a **Proteção contra Injeção de Código SQL (SQL Injection)** na camada de integração da API.

1. Princípio do Menor Privilégio e Gestão de Roles no PostgreSQL

A aplicação Node.js **jamais deve se conectar ao banco de dados utilizando o usuário superadministrador (`postgres`)**. Cada serviço deve possuir um usuário (Role) com privilégios restritos apenas ao esquema e tabelas necessárias. 

-- Criação de um Role específico para a aplicação Back-End
CREATE ROLE app_b2b_user WITH LOGIN PASSWORD 'senha_forte_env';

-- Concessão de privilégios mínimos apenas nas tabelas do esquema público
GRANT CONNECT ON DATABASE portal_b2b TO app_b2b_user;
GRANT USAGE ON SCHEMA public TO app_b2b_user;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO app_b2b_user;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO app_b2b_user;

2. Vulnerabilidade de SQL Injection: O Perigo da Concatenação

SQL Injection (SQLi) ocorre quando dados não sanitizados inseridos pelo usuário são concatenados diretamente na string de consulta SQL, permitindo que um atacante altere a semântica da query.

VULNERÁVEL Concatenação Direta

O atacante envia o e-mail: ' OR '1'='1' --
A query resultante ignora o filtro e retorna todos os registros ou altera dados indevidamente.

PROTEGIDO Consultas Parametrizadas

Uso de Prepared Statements com marcadores de posição ($1, $2). Os parâmetros são enviados separadamente e tratados estritamente como literais de dados pelo PostgreSQL.

🚨 Código Vulnerável (NUNCA UTILIZE):
const query = `SELECT * FROM clientes_b2b WHERE email = '${req.body.email}'`;
Se email for admin@b2b.com' --, o restante da verificação é anulado!
✅ Código Seguro e Imunizado (Prepared Statement):
const query = 'SELECT * FROM clientes_b2b WHERE email = $1';
const values = [req.body.email];
const result = await db.query(query, values);
02

Conexão do Node.js ao PostgreSQL: Driver `pg`, Pool e Variables de Ambiente

⏱️ Duração Estimada: 60 min

Para integrar uma aplicação Node.js ao banco PostgreSQL, utilizamos o driver oficial de alta performance `pg` (node-postgres) configurado com **Pool de Conexões** e gerenciamento seguro de credenciais via **`dotenv`**.

1. Por que utilizar Pool de Conexões em vez de Client Único?

Abrir e fechar uma conexão física com o banco de dados a cada requisição HTTP é uma operação custosa que consome memória e CPU. O Connection Pool (Pool de Conexões) mantém um grupo de conexões abertas e reutilizáveis na memória, distribuindo-as de forma concorrente conforme as requisições chegam à API.

Estratégia Mecanismo Desempenho & Escalabilidade Recomendação
new Client() Abre 1 conexão dedicada manualmente. Deve ser aberta e encerrada explicitamente. Baixo. Sofre gargalo grave sob múltiplas requisições simultâneas. Apenas para scripts de migração DDL isolados.
new Pool() Gerencia um conjunto dinâmico de conexões reutilizáveis automaticamente. Altíssimo. Suporta milhares de requisições paralelas reutilizando soquetes. Padrão obrigatório para aplicações Web / APIs.

2. Configuração Completa do Módulo de Conexão no Projeto

A. Instalação das Dependências no Terminal:

npm install pg dotenv

B. Variáveis de Ambiente no arquivo `.env` (NUNCA comitadas no Git!): 

DB_HOST=localhost
DB_PORT=5432
DB_USER=app_b2b_user
DB_PASSWORD=senha_segura_123
DB_NAME=portal_b2b
DB_POOL_MAX=20

C. Módulo de Conexão Centralizado (`src/config/db.js`): 

import pkg from 'pg';
import dotenv from 'dotenv';

dotenv.config();

const { Pool } = pkg;

// Instanciação do Pool reutilizável com variáveis de ambiente
const pool = new Pool({
  host: process.env.DB_HOST,
  port: Number(process.env.DB_PORT) || 5432,
  user: process.env.DB_USER,
  password: process.env.DB_PASSWORD,
  database: process.env.DB_NAME,
  max: Number(process.env.DB_POOL_MAX) || 10,
  idleTimeoutMillis: 30000,
  connectionTimeoutMillis: 2000,
});

// Evento para monitorar erros inesperados em clientes inativos do pool
pool.on('error', (err) => {
  console.error('❌ Erro inesperado no Pool de Conexões do PostgreSQL:', err);
});

// Função auxiliar genérica exportada para execução de queries parametrizadas
export const query = (text, params) => pool.query(text, params);

export default pool;

D. Script de Teste de Conexão (`src/test-db.js`): 

import { query } from './config/db.js';

async function testarConexao() {
  try {
    const res = await query('SELECT NOW() AS data_atual, current_database() AS banco_conectado');
    console.log('✅ Conexão estabelecida com sucesso!');
    console.log('📅 Data/Hora no PostgreSQL:', res.rows[0].data_atual);
    console.log('🗄️ Banco de Dados:', res.rows[0].banco_conectado);
  } catch (err) {
    console.error('❌ Falha na conexão com o banco de dados:', err.message);
  }
}

testarConexao();

Encerramento: Glossário da Aula + Quiz Final de Fixação

⏱️ Duração Estimada: 30 min

📚 Glossário Técnico da Aula

SQL Injection (SQLi)

Ataque de injeção de código em que comandos SQL maliciosos são inseridos nos campos de entrada da aplicação para manipular o banco.

Prepared Statement

Instrução SQL pré-compilada no banco onde parâmetros são separados do comando, imunizando o código contra SQL Injection.

Connection Pool

Gerenciador de um grupo mantido de conexões ativas reutilizáveis com a base de dados, otimizando recursos do servidor.

dotenv

Módulo Node.js que carrega variáveis de ambiente de um arquivo `.env` para o objeto `process.env`, protegendo credenciais sensíveis.

❓ Quiz Final de Fixação

1. Por que a instrução `db.query('SELECT * FROM clientes WHERE email = ' + email)` é considerada uma grave falha de segurança?
A) Porque reduz a velocidade do banco de dados em até 50%.
B) Porque abre brecha para ataques de SQL Injection, pois concatena dados enviados pelo usuário diretamente na instrução SQL.
C) Porque impede o uso de índices de chave primária.
D) Porque obriga o encerramento do Pool de Conexões.
✅ Resposta Correta: B) Porque abre brecha para ataques de SQL Injection.
Justificativa: Concatenar strings no código SQL permite que entradas maliciosas modifiquem a lógica da consulta. O correto é usar consultas parametrizadas (`$1`, `$2`).
2. Qual é a principal vantagem de utilizar um `Pool` de conexões em vez de instanciar um `Client` individual a cada requisição em uma API Node.js?
A) O Pool criptografa automaticamente as senhas no arquivo `.env`.
B) O Pool elimina a necessidade de definir chaves primárias nas tabelas.
C) O Pool reutiliza conexões abertas, evitando o alto custo de abrir e fechar conexões físicas para cada requisição HTTP.
D) O Pool substitui as rotas do Express.js por rotas automáticas de banco.
✅ Resposta Correta: C) O Pool reutiliza conexões abertas.
Justificativa: Abrir e fechar conexões físicas gera latência e alto consumo de recursos. O Pool otimiza o desempenho mantendo um conjunto de conexões prontas para uso.
3. Onde devem ser armazenadas credenciais sensíveis como senhas de banco de dados e portas em uma aplicação Node.js profissional?
A) Diretamente no código fonte no arquivo `db.js` e comitadas no GitHub.
B) Em comentários no topo do arquivo `schema.sql`.
C) Em variáveis de ambiente no arquivo `.env`, o qual deve estar incluído no arquivo `.gitignore`.
D) No arquivo `package.json` dentro do campo `scripts`.
✅ Resposta Correta: C) Em variáveis de ambiente no arquivo `.env`, o qual deve estar no `.gitignore`.
Justificativa: Credenciais nunca devem ser expostas em repositórios. O arquivo `.env` mantém as configurações locais e é ignorado pelo Git via `.gitignore`.
