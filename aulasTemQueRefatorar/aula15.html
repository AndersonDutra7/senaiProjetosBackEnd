01

Camada de Acesso a Dados (DAO / Repository Pattern)

⏱️ Duração Estimada: 60 min

À medida que a aplicação cresce, escrever queries SQL diretamente nos Models pode gerar duplicação de código e dificultar a troca ou evolução do mecanismo de persistência. A criação de uma Camada de Acesso a Dados (DAO / Repository Pattern) encapsula completamente os detalhes técnicos do SGBD.

1. Padrão Repository vs. Acesso Direto

REPOSITORY PATTERN

Atua como uma coleção em memória de objetos de domínio. Isola as regras de negócio de como os dados são lidos ou persistidos no banco de dados.

DAO (Data Access Object)

Mapeia operações brutas de tabela (CRUD) para métodos JavaScript assíncronos (`async/await`), ocultando comandos `SELECT`, `INSERT`, `UPDATE` e `DELETE`.

2. Implementação do Repository com Abstração de Conexão (`src/repositories/pedidoRepository.js`)

import { query } from '../config/db.js';

export const pedidoRepository = {
  // Busca pedido completo com dados do cliente e itens agregados em JSON
  buscarPorIdCompleto: async (idPedido) => {
    const text = `
      SELECT 
        p.id_pedido,
        p.data_pedido,
        p.status_pedido,
        p.valor_total,
        json_build_object(
          'id_cliente', c.id_cliente,
          'cnpj', c.cnpj,
          'razao_social', c.razao_social,
          'email', c.email
        ) AS cliente,
        COALESCE(
          json_agg(
            json_build_object(
              'id_produto', pr.id_produto,
              'codigo_sku', pr.codigo_sku,
              'nome_produto', pr.nome_produto,
              'quantidade', ip.quantidade,
              'preco_unitario', ip.preco_unitario_momento,
              'subtotal', (ip.quantidade * ip.preco_unitario_momento)
            )
          ) FILTER (WHERE pr.id_produto IS NOT NULL), '[]'
        ) AS itens
      FROM pedidos p
      INNER JOIN clientes_b2b c ON p.id_cliente = c.id_cliente
      LEFT JOIN itens_pedido ip ON p.id_pedido = ip.id_pedido
      LEFT JOIN produtos pr ON ip.id_produto = pr.id_produto
      WHERE p.id_pedido = $1
      GROUP BY p.id_pedido, c.id_cliente;
    `;
    const result = await query(text, [idPedido]);
    return result.rows[0];
  }
};
💡 Vantagem do `json_build_object` e `json_agg`: O PostgreSQL realiza a agregação e montagem dos objetos filhos diretamente no motor de banco de dados, enviando para o Node.js uma estrutura JSON pronta e de altíssima performance.

Tratamento de Requisições, Códigos do PostgreSQL e Middleware Global de Erros

⏱️ Duração Estimada: 60 min

Uma API profissional não deve expor *stack traces* de erros de banco de dados nem quebrar durante exceções não tratadas. As exceções lançadas pelo PostgreSQL possuem códigos numéricos padronizados (SQLSTATE) que devem ser traduzidos em **respostas HTTP claras e informativas**.

1. Mapeamento das Exceções mais Comuns do PostgreSQL

Código PostgreSQL (SQLSTATE) Nome do Erro Causa no Sistema B2B Status HTTP Correspondente
23505 unique_violation Tentativa de cadastrar um CNPJ, E-mail ou SKU que já existe no banco. 409 Conflict
23503 foreign_key_violation Tentar vincular um pedido a um `id_cliente` inexistente ou deletar cliente com pedidos associados. 400 Bad Request / 422 Unprocessable
23514 check_violation Tentar cadastrar preço negativo ou quantidade de item igual a zero (`CHECK`). 400 Bad Request
22P02 invalid_text_representation Enviar texto ou caractere inválido para um campo de ID do tipo numérico/BIGINT. 400 Bad Request

2. Middleware Global de Tratamento de Erros (`src/middlewares/errorHandler.js`)

// Middleware Global de Erros do Express (quatro parâmetros obrigatórios: err, req, res, next)
export const errorHandler = (err, req, res, next) => {
  console.error('❌ [LOG DE ERRO GLOBAL]:', err);

  // Erros de violação do PostgreSQL
  if (err.code === '23505') {
    return res.status(409).json({
      success: false,
      error_code: 'DUPLICATE_ENTRY',
      message: 'Já existe um registro cadastrado com o mesmo identificador único (CNPJ, E-mail ou SKU).'
    });
  }

  if (err.code === '23503') {
    return res.status(400).json({
      success: false,
      error_code: 'FOREIGN_KEY_VIOLATION',
      message: 'A entidade pai referenciada não existe ou possui dependências ativas.'
    });
  }

  if (err.code === '22P02') {
    return res.status(400).json({
      success: false,
      error_code: 'INVALID_INPUT_FORMAT',
      message: 'Formato de dado inválido fornecido nos parâmetros da requisição.'
    });
  }

  // Erro genérico padrão de servidor
  return res.status(err.status || 500).json({
    success: false,
    error_code: 'INTERNAL_SERVER_ERROR',
    message: err.message || 'Ocorreu um erro interno inesperado no servidor.'
  });
};
⚠️ Regra do Express: O middleware global de erro DEVE possuir exatamente quatro argumentos: (err, req, res, next) e ser registrado em app.use(errorHandler) **APÓS todas as declarações de rotas** no arquivo app.js!

Desafio Prático — Integração Completa e Transação Atômica de Pedidos B2B

⏱️ Duração Estimada: 60 min

A criação de um Pedido de Venda B2B exige a inserção do cabeçalho (`pedidos`), inserção dos itens (`itens_pedido`) e atualização do saldo em estoque (`inventario`). Se qualquer um desses passos falhar, **TUDO deve ser cancelado**. Isso exige o uso de **Transações SQL com Client Dedicado do Pool**.

1. Padrão de Transação Atômica com `pool.connect()` (`src/models/pedidoModel.js`)

import pool from '../config/db.js';

export const pedidoModel = {
  // Transação Atômica Completa: Pedido + Itens + Abate de Estoque
  criarPedidoCompleto: async (idCliente, itens) => {
    // 1. Solicita um Client exclusivo do Pool de Conexões
    const client = await pool.connect();

    try {
      // 2. Inicia o Bloco Transacional
      await client.query('BEGIN');

      // A. Inserção do Cabeçalho do Pedido
      const resPedido = await client.query(
        'INSERT INTO pedidos (id_cliente, status_pedido, valor_total) VALUES ($1, $2, $3) RETURNING *',
        [idCliente, 'CONFIRMADO', 0.00]
      );
      const novoPedido = resPedido.rows[0];
      let valorTotalPedido = 0;

      // B. Loop de Inserção dos Itens e Atualização do Saldo do Inventário
      for (const item of itens) {
        // Busca preço atual e verifica saldo em estoque
        const resProduto = await client.query(
          'SELECT p.preco_base, i.quantidade_saldo FROM produtos p JOIN inventario i ON p.id_produto = i.id_produto WHERE p.id_produto = $1 FOR UPDATE',
          [item.id_produto]
        );

        if (resProduto.rows.length === 0) {
          throw new Error(`Produto ID ${item.id_produto} não localizado.`);
        }

        const { preco_base, quantidade_saldo } = resProduto.rows[0];

        if (quantidade_saldo < item.quantidade) {
          throw new Error(`Estoque insuficiente para o produto ID ${item.id_produto}. Saldo atual: ${quantidade_saldo}`);
        }

        const subtotal = preco_base * item.quantidade;
        valorTotalPedido += subtotal;

        // Inserção do Item do Pedido
        await client.query(
          'INSERT INTO itens_pedido (id_pedido, id_produto, quantidade, preco_unitario_momento) VALUES ($1, $2, $3, $4)',
          [novoPedido.id_pedido, item.id_produto, item.quantidade, preco_base]
        );

        // Abate de Estoque no Inventário
        await client.query(
          'UPDATE inventario SET quantidade_saldo = quantidade_saldo - $1 WHERE id_produto = $2',
          [item.quantidade, item.id_produto]
        );
      }

      // C. Atualização do Valor Total Final do Pedido
      await client.query(
        'UPDATE pedidos SET valor_total = $1 WHERE id_pedido = $2',
        [valorTotalPedido, novoPedido.id_pedido]
      );

      // 3. Efetiva todas as operações no banco de dados
      await client.query('COMMIT');
      novoPedido.valor_total = valorTotalPedido;
      return novoPedido;

    } catch (error) {
      // 4. Em caso de falha, desfaz todas as alterações ocorridas na transação!
      await client.query('ROLLBACK');
      throw error;
    } finally {
      // 5. OBRIGATÓRIO: Devolve o Client de volta para o Pool
      client.release();
    }
  }
};

Encerramento: Glossário da Aula + Quiz Final de Fixação

⏱️ Duração Estimada: 30 min

📚 Glossário Técnico da Aula

Repository Pattern

Camada de abstração entre as regras de negócio e a persistência, simulando uma coleção em memória de entidades.

Transação SQL (ACID)

Unidade lógica de trabalho delimitada por `BEGIN`, `COMMIT` e `ROLLBACK` que garante a propriedade de atomicidade (tudo ou nada).

SQLSTATE 23505

Código de erro nativo do PostgreSQL indicando violação de restrição `UNIQUE` (tentativa de duplicar dados únicos).

client.release()

Método crucial invocado no bloco `finally` para devolver uma conexão individual do `pg.Pool` de volta ao gerenciador.

❓ Quiz Final de Fixação

1. Em uma operação de fechamento de pedido que envolve gravar o pedido, gravar os itens e dar baixa no estoque, o que ocorre se o comando ROLLBACK for executado no bloco catch?
A) O pedido é gravado, mas os itens são apagados do banco.
B) Todas as alterações realizadas desde o comando BEGIN são completamente desfeitas, restaurando o banco ao estado original.
C) O banco de dados é desligado imediatamente por segurança.
D) O estoque é zerado automaticamente.
✅ Resposta Correta: B) Todas as alterações desde o BEGIN são completamente desfeitas.
Justificativa: O comando `ROLLBACK` garante a atomicidade da transação. Se houver falha em qualquer etapa, nada é salvo.
2. Qual é a utilidade prática de criar um Middleware Global de Erros no Express.js com a assinatura `(err, req, res, next)`?
A) Executar consultas SQL mais rapidamente.
B) Interceptar exceções não tratadas da aplicação em um único ponto, traduzindo códigos de erro como SQLSTATE 23505 em respostas HTTP sem expor stack traces.
C) Substituir a necessidade do arquivo `.env`.
D) Validar automaticamente o formato do CNPJ.
✅ Resposta Correta: B) Interceptar exceções não tratadas em um único ponto e traduzir em respostas HTTP adequadas.
Justificativa: O middleware global centraliza a gestão de exceções da API, padronizando os retornos JSON de erro para o cliente.
3. O que acontece se o desenvolvedor utilizar `const client = await pool.connect()` para realizar uma transação e ESQUECER de chamar `client.release()` no bloco `finally`?
A) O código funciona normalmente sem nenhum efeito colateral.
B) A conexão fica "vazada" (connection leak), esgotando as conexões do Pool e travando a API após algumas requisições.
C) O PostgreSQL apaga a tabela afetada.
D) O servidor Node.js reinicia automaticamente.
✅ Resposta Correta: B) A conexão fica vazada (connection leak), esgotando o Pool.
Justificativa: Chamar `client.release()` no bloco `finally` é essencial para liberar a conexão de volta ao Pool. Sem isso, novas requisições ficarão bloqueadas aguardando conexões.
