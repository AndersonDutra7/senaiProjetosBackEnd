01

Autenticação com JWT e Criptografia de Senhas (`bcrypt`)

⏱️ Duração Estimada: 60 min

A proteção de credenciais de usuários e a verificação de identidade em APIs Web modernas exigem mecanismos de segurança rigorosos. Senhas **jamais podem ser salvas em texto puro** nem criptografadas com algoritmos reversíveis.

1. Criptografia Unidirecional (Hashing) com `bcrypt` e Salting

O bcrypt é um algoritmo de hashing adaptativo projetado especificamente para proteção de senhas. Ele aplica uma técnica chamada Salting (adição de uma string aleatória antes do hash) e um fator de custo (rounds) para prevenir ataques de dicionário e *Rainbow Tables*.

Incorreto: Criptografia Reversível / Texto Puro

Salvar senhas como "senha123" ou usar algoritmos reversíveis (Ex: Base64, AES) permite que qualquer vazamento de banco exponha todas as senhas dos clientes B2B.

Correto: Hash Irreversível (`bcrypt`)

O `bcrypt` gera uma hash de 60 caracteres (Ex: $2b$10$e8N8y...). O processo é irreversível: o sistema apenas compara a senha digitada com a hash guardada via bcrypt.compare().

// Instalação das dependências de segurança
npm install bcryptjs jsonwebtoken cors
import bcrypt from 'bcryptjs';

// 1. Criptografando a senha durante o cadastro do usuário
const saltRounds = 10; // Fator de custo balanceado (computacionalmente seguro)
const senhaTextoPuro = 'SenhaSegura123!';
const hashSenha = await bcrypt.hash(senhaTextoPuro, saltRounds);

// 2. Comparando a senha digitada no Login com a Hash salva no banco
const senhaDigitada = 'SenhaSegura123!';
const senhaValida = await bcrypt.compare(senhaDigitada, hashSenha); // Retorna true ou false

2. Arquitetura do JSON Web Token (JWT) — Autenticação Stateless

O JWT (JSON Web Token) é um padrão aberto (RFC 7519) para transmissão segura de declarações (*claims*) entre partes no formato JSON. Por ser **Stateless** (sem estado no servidor), a API não precisa guardar sessões em memória.

Parte do Token Conteúdo / Estrutura Função na Segurança
Header (Cabeçalho) JSON codificado em Base64Url contendo o algoritmo (ex: HS256) e tipo. Informa como o token foi assinado.
Payload (Carga útil) JSON em Base64Url com dados do usuário (id_usuario, email, perfil) e expiração. Carrega as informações de identificação (claims publicas). **Não coloque senhas aqui!**
Signature (Assinatura) Hash criptográfico combinando Header + Payload + Chave Secreta (`JWT_SECRET`). Garante a **integridade**: se qualquer caractere do token for alterado, a assinatura se torna inválida.
💡 Estrutura de um Token JWT: header.payload.signature (três partes separadas por pontos).

Boas Práticas de Segurança na Comunicação Web (CORS, Proteção e `.env`)

⏱️ Duração Estimada: 60 min

Proteger uma API vai além da autenticação de usuários. Envolve configurar adequadamente a política de origem cruzada (**CORS**) e proteger chaves mestras e variáveis de ambiente contra vazamentos.

1. Configuração do Middleware CORS (`cors`) no Express

Por padrão, navegadores web bloqueiam requisições AJAX/Fetch feitas a partir de domínios diferentes da API devido à **Same-Origin Policy (SOP)**. O middleware cors especifica quais origens confiáveis podem consumir a API. 

import express from 'express';
import cors from 'cors';

const app = express();

// Configuração estrita do CORS para produção B2B
const corsOptions = {
  origin: process.env.FRONTEND_URL || 'http://localhost:5173', // Apenas o frontend autorizado
  methods: ['GET', 'POST', 'PUT', 'DELETE'],
  allowedHeaders: ['Content-Type', 'Authorization'],
  credentials: true
};

app.use(cors(corsOptions));

2. Gerenciamento Seguro de Segredos no `.env` e `.gitignore`

A chave secreta usada para assinar o JWT (JWT_SECRET) deve ser uma string longa, complexa e mantida em segredo absoluto.

Desafio Prático — Implementação do Módulo de Login e Middleware de Autenticação

⏱️ Duração Estimada: 60 min

1. Model do Usuário/Autenticação (`src/models/usuarioModel.js`)

import { query } from '../config/db.js';
import bcrypt from 'bcryptjs';

export const usuarioModel = {
  // Cadastra um novo usuário criptografando a senha com bcrypt
  criar: async ({ nome, email, senha, perfil }) => {
    const hashSenha = await bcrypt.hash(senha, 10);
    const text = `
      INSERT INTO usuarios (nome, email, senha, perfil)
      VALUES ($1, $2, $3, $4)
      RETURNING id_usuario, nome, email, perfil, criado_em
    `;
    const result = await query(text, [nome, email, hashSenha, perfil || 'CLIENTE']);
    return result.rows[0];
  },

  // Busca usuário por e-mail (incluindo a hash da senha para verificação)
  buscarPorEmail: async (email) => {
    const text = 'SELECT * FROM usuarios WHERE email = $1 AND ativo = TRUE';
    const result = await query(text, [email]);
    return result.rows[0];
  }
};

2. Controller de Autenticação (`src/controllers/authController.js`)

import jwt from 'jsonwebtoken';
import bcrypt from 'bcryptjs';
import { usuarioModel } from '../models/usuarioModel.js';

export const authController = {
  registrar: async (req, res) => {
    try {
      const { nome, email, senha, perfil } = req.body;
      if (!nome || !email || !senha) {
        return res.status(400).json({ success: false, message: 'Nome, E-mail e Senha são obrigatórios.' });
      }

      const usuarioExistente = await usuarioModel.buscarPorEmail(email);
      if (usuarioExistente) {
        return res.status(409).json({ success: false, message: 'Este e-mail já está em uso.' });
      }

      const novoUsuario = await usuarioModel.criar({ nome, email, senha, perfil });
      return res.status(201).json({ success: true, message: 'Usuário cadastrado com sucesso!', data: novoUsuario });
    } catch (error) {
      console.error('❌ Erro no authController.registrar:', error);
      return res.status(500).json({ success: false, message: 'Erro ao registrar usuário.' });
    }
  },

  login: async (req, res) => {
    try {
      const { email, senha } = req.body;
      if (!email || !senha) {
        return res.status(400).json({ success: false, message: 'E-mail e senha são obrigatórios.' });
      }

      const usuario = await usuarioModel.buscarPorEmail(email);
      if (!usuario) {
        return res.status(401).json({ success: false, message: 'Credenciais inválidas.' });
      }

      // Validação da senha com bcrypt
      const senhaValida = await bcrypt.compare(senha, usuario.senha);
      if (!senhaValida) {
        return res.status(401).json({ success: false, message: 'Credenciais inválidas.' });
      }

      // Geração do Token JWT com validade estipulada
      const token = jwt.sign(
        { id_usuario: usuario.id_usuario, email: usuario.email, perfil: usuario.perfil },
        process.env.JWT_SECRET,
        { expiresIn: process.env.JWT_EXPIRES_IN || '8h' }
      );

      return res.status(200).json({
        success: true,
        message: 'Login realizado com sucesso!',
        token,
        usuario: { id_usuario: usuario.id_usuario, nome: usuario.nome, email: usuario.email, perfil: usuario.perfil }
      });
    } catch (error) {
      console.error('❌ Erro no authController.login:', error);
      return res.status(500).json({ success: false, message: 'Erro ao realizar login.' });
    }
  }
};

3. Middleware de Proteção de Rotas (`src/middlewares/authMiddleware.js`)

import jwt from 'jsonwebtoken';

export const autenticarToken = (req, res, next) => {
  // Captura do Header Authorization (Formato: "Bearer TOKEN_JWT_AQUI")
  const authHeader = req.headers['authorization'];
  const token = authHeader && authHeader.split(' ')[1];

  if (!token) {
    return res.status(401).json({ success: false, message: 'Acesso negado. Token de autenticação não fornecido.' });
  }

  try {
    // Validação e verificação de assinatura/expiração do JWT
    const decoded = jwt.verify(token, process.env.JWT_SECRET);
    req.usuario = decoded; // Injeta os dados do usuário autenticado no objeto req
    next(); // Permite a passagem para a próxima função/controller
  } catch (error) {
    return res.status(403).json({ success: false, message: 'Token de autenticação inválido ou expirado.' });
  }
};

4. Aplicação do Middleware nas Rotas Privadas

import { Router } from 'express';
import { pedidoController } from '../controllers/pedidoController.js';
import { autenticarToken } from '../middlewares/authMiddleware.js';

const router = Router();

// Apenas usuários autenticados com JWT podem criar ou listar pedidos!
router.post('/', autenticarToken, pedidoController.criarPedido);
router.get('/', autenticarToken, pedidoController.listarPedidos);

export default router;

📚 Glossário Técnico da Aula

bcrypt

Algoritmo de hashing adaptativo irreversível com suporte nativo a Salting, ideal para armazenamento seguro de senhas.

JWT (JSON Web Token)

Padrão compacto e autocontido para transmissão segura de dados de autenticação em formato JSON assinado digitalmente.

CORS (Cross-Origin Resource Sharing)

Mecanismo do navegador que utiliza cabeçalhos HTTP para permitir ou restringir o acesso a recursos de um domínio diferente.

Bearer Token

Esquema de autenticação HTTP onde o cliente envia o token de acesso no cabeçalho `Authorization: Bearer `.

❓ Quiz Final de Fixação

1. Por que algoritmos de criptografia reversível (que permitem descriptografar a senha) NÃO devem ser utilizados para guardar senhas no banco de dados?
A) Porque a criptografia reversível ocupa muito espaço no disco rígido.
B) Porque se um atacante obtiver a chave de descriptografia ou o arquivo do banco, todas as senhas dos usuários poderão ser recuperadas em texto puro.
C) Porque o Node.js não suporta criptografia reversível.
D) Porque o PostgreSQL não aceita senhas descriptografadas.
✅ Resposta Correta: B) Porque o vazamento da chave permite expor todas as senhas.
Justificativa: O correto é utilizar hashing irreversível (`bcrypt`). A senha nunca é descriptografada; apenas compara-se a hash gerada na tentativa de login.
2. Qual é o papel da Assinatura (Signature) em um Token JWT e o que ocorre se um usuário malicioso tentar alterar o seu perfil de "CLIENTE" para "ADMIN" dentro do Payload?
A) A assinatura é atualizada automaticamente no navegador do cliente.
B) A assinatura torna-se incompatível com o hash recalculado pelo servidor via `JWT_SECRET`, e a API rejeita a requisição com status `403 Forbidden`.
C) O banco de dados altera o perfil do usuário para ADMIN automaticamente.
D) O token passa a valer por tempo indeterminado.
✅ Resposta Correta: B) A assinatura torna-se incompatível e a API rejeita a requisição.
Justificativa: A assinatura valida a integridade do token. Qualquer alteração nos dados do Payload invalida a verificação do servidor.
3. Como o middleware de autenticação `autenticarToken` valida o usuário em uma rota privada como `POST /api/v1/pedidos`?
A) Consultando o arquivo `.env` para ver a lista de e-mails permitidos.
B) Extraindo o JWT do cabeçalho `Authorization: Bearer `, verificando sua validade com `jwt.verify` e injetando o usuário autenticado no objeto `req.usuario`.
C) Solicitando novamente a senha do usuário a cada requisição de pedido.
D) Desligando a conexão do PostgreSQL temporariamente.
✅ Resposta Correta: B) Extraindo o JWT do cabeçalho Authorization e verificando com `jwt.verify`.
Justificativa: O middleware intercepta a requisição HTTP, extrai o Bearer token, valida sua chave e expiração e autoriza o prosseguimento se válido.
