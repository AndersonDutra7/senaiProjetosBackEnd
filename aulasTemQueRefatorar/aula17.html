01

Validação de Dados de Entrada (Middlewares de Validação)

⏱️ Duração Estimada: 60 min

Uma das principais diretrizes de segurança e qualidade de software é: "Nunca confie nos dados enviados pelo cliente". Dados de entrada malformados, tipos incorretos ou ausentes podem causar *crashes* na aplicação, vulnerabilidades de segurança ou corrupção de dados no banco PostgreSQL.

1. Princípio da Validação na Borda (Edge Validation)

A validação deve ocorrer na **borda da requisição (camada de rotas/middlewares)**, antes mesmo que os dados cheguem aos Controllers e Models. Isso economiza processamento e recursos de banco de dados.

Sem Middleware de Validação

O dado entra na API, passa pelo Controller, tenta rodar no Model, falha no banco de dados com erro de tipo (SQLSTATE) e consome conexões do Pool antes de rejeitar.

Com Middleware de Validação (Zod)

O schema valida req.body no início da requisição. Se houver erro, a API responde imediatamente com 400 Bad Request contendo a lista detalhada de campos incorretos.

2. Validação Estrita de Schemas com a Biblioteca `zod`

A biblioteca Zod permite declarar schemas de validação com inferência automática de tipos e mensagens customizadas em português.

npm install zod

A. Definição do Schema de Validação de Cliente B2B (`src/schemas/clienteSchema.js`):

import { z } from 'zod';

export const criarClienteSchema = z.object({
  cnpj: z
    .string({ required_error: 'O CNPJ é obrigatório.' })
    .length(14, 'O CNPJ deve conter exatamente 14 dígitos numéricos.')
    .regex(/^\d+$/, 'O CNPJ deve conter apenas números.'),

  razao_social: z
    .string({ required_error: 'A Razão Social é obrigatória.' })
    .min(3, 'A Razão Social deve ter no mínimo 3 caracteres.')
    .max(150, 'A Razão Social não pode exceder 150 caracteres.'),

  email: z
    .string({ required_error: 'O e-mail é obrigatório.' })
    .email('Formato de e-mail inválido.'),

  telefone: z
    .string()
    .optional()
});

B. Middleware Genérico de Validação (`src/middlewares/validateSchema.js`):

export const validateSchema = (schema) => (req, res, next) => {
  try {
    // Valida e sanitiza req.body contra o schema definido
    req.body = schema.parse(req.body);
    next(); // Dados válidos! Prossegue para o Controller.
  } catch (error) {
    // Formata os erros do Zod em um array amigável
    const errosFormatados = error.errors.map((err) => ({
      campo: err.path.join('.'),
      mensagem: err.message
    }));

    return res.status(400).json({
      success: false,
      error_code: 'VALIDATION_ERROR',
      message: 'Dados de entrada inválidos.',
      errors: errosFormatados
    });
  }
};
02

Tratamento Centralizado de Erros e Padronização de Respostas

⏱️ Duração Estimada: 60 min

Para manter uma arquitetura limpa e previsível, a aplicação deve adotar uma **Classe de Erro Operacional Customizada (`AppError`)** e um **Envelope Padrão de Resposta JSON** para toda a API.

1. A Classe `AppError` para Exceções de Negócio (`src/errors/AppError.js`)

Erros conhecidos da aplicação (ex: cliente não encontrado, estoque insuficiente, credenciais inválidas) são **Erros Operacionais**. Criamos uma classe que herda de Error estipulando o status HTTP correspondente. 

export class AppError extends Error {
  constructor(message, statusCode = 400, errorCode = 'BAD_REQUEST') {
    super(message);
    this.statusCode = statusCode;
    this.errorCode = errorCode;
    this.isOperational = true; // Diferencia erros conhecidos de falhas inesperadas de código
    Error.captureStackTrace(this, this.constructor);
  }
}

2. Padronização Global do Envelope de Resposta JSON

Todas as rotas da API B2B devem seguir uma estrutura de resposta consistente, tanto para sucesso quanto para falhas:

Tipo de Resposta Estrutura JSON do Envelope Exemplo de Uso
SUCESSO (2xx) { success: true, message: "...", data: { ... } } 200 OK em buscas / 201 Created no cadastro.
ERRO OPERACIONAL (4xx) { success: false, error_code: "...", message: "..." } 404 Not Found, 401 Unauthorized, 409 Conflict.
ERRO INTERNO (500) { success: false, error_code: "INTERNAL_SERVER_ERROR", message: "..." } Falhas de conexão com banco, exceções não tratadas de código.

3. Reformulação do Middleware Global de Erros (`src/middlewares/errorHandler.js`)

import { AppError } from '../errors/AppError.js';

export const errorHandler = (err, req, res, next) => {
  // 1. Tratamento de Exceções Operacionais do AppError
  if (err instanceof AppError) {
    return res.status(err.statusCode).json({
      success: false,
      error_code: err.errorCode,
      message: err.message
    });
  }

  // 2. Tratamento de Erros Nativos de Violação do PostgreSQL
  if (err.code === '23505') {
    return res.status(409).json({
      success: false,
      error_code: 'DUPLICATE_ENTRY',
      message: 'Conflito: registro já existente no banco de dados.'
    });
  }

  console.error('💥 [ERRO NÃO TRATADO DE SERVIDOR]:', err);

  // 3. Fallback para Erros Inesperados (500)
  return res.status(500).json({
    success: false,
    error_code: 'INTERNAL_SERVER_ERROR',
    message: 'Ocorreu um erro interno inesperado no servidor.'
  });
};

Desafio Prático — Implementação de Validações e Erros no Projeto B2B

⏱️ Duração Estimada: 60 min

Nesta atividade prática, as equipes integrarão o middleware de validação com `zod` em todas as rotas e refatorarão os Controllers para utilizar a classe `AppError`.

1. Refatoração do Controller usando `AppError` (`src/controllers/clienteController.js`)

import { clienteModel } from '../models/clienteModel.js';
import { AppError } from '../errors/AppError.js';

export const clienteController = {
  obterPorId: async (req, res, next) => {
    try {
      const { id } = req.params;
      const cliente = await clienteModel.buscarPorId(id);

      if (!cliente) {
        // Lança o AppError operacional e repassa para o next()
        throw new AppError('Cliente não encontrado com o ID informado.', 404, 'CLIENT_NOT_FOUND');
      }

      return res.status(200).json({ success: true, data: cliente });
    } catch (error) {
      next(error); // Encaminha para o middleware global de erros!
    }
  },

  criar: async (req, res, next) => {
    try {
      // Nota: O req.body já foi pré-validado e sanitizado pelo validateSchema!
      const novoCliente = await clienteModel.criar(req.body);
      return res.status(201).json({ success: true, message: 'Cliente cadastrado!', data: novoCliente });
    } catch (error) {
      next(error);
    }
  }
};

2. Mapeamento das Rotas com Middleware de Validação (`src/routes/clienteRoutes.js`)

import { Router } from 'express';
import { clienteController } from '../controllers/clienteController.js';
import { validateSchema } from '../middlewares/validateSchema.js';
import { criarClienteSchema } from '../schemas/clienteSchema.js';

const router = Router();

// A rota valida os dados de entrada ANTES de acionar o Controller!
router.post('/', validateSchema(criarClienteSchema), clienteController.criar);
router.get('/:id', clienteController.obterPorId);

export default router;

Encerramento: Glossário da Aula + Quiz Final de Fixação

⏱️ Duração Estimada: 30 min

📚 Glossário Técnico da Aula

Zod / Schema Validation

Biblioteca de declaração e validação de schemas em TypeScript/JavaScript com inferência automática e tratamento de borda.

AppError (Erro Operacional)

Classe customizada de erro para representar falhas previsíveis de regra de negócio associadas a status HTTP adequados.

Sanitização de Dados

Processo de limpar, remover caracteres indesejados e ajustar o formato das entradas do usuário antes do processamento.

Envelope JSON Padronizado

Padrão estrutural de resposta da API (`success`, `message`, `data`/`errors`) mantido uniformemente em todas as rotas.

❓ Quiz Final de Fixação

1. Qual é a principal vantagem de executar a validação de dados de entrada via middlewares (como Zod) antes de alcançar os Controllers e Models?
A) Aumentar o tamanho do banco de dados PostgreSQL.
B) Barrar requisições malformadas na borda da aplicação, evitando o desperdício de processamento e conexões do banco.
C) Eliminar a necessidade de usar o protocolo HTTP.
D) Substituir a camada de rotas do Express.
✅ Resposta Correta: B) Barrar requisições malformadas na borda da aplicação.
Justificativa: Validar schemas na borda previne falhas graves e economiza recursos do servidor e do Pool de conexões do PostgreSQL.
2. O que caracteriza um "Erro Operacional" representado pela classe `AppError` em oposição a uma falha inesperada de código?
A) Um erro operacional é uma falha previsível de regra de negócio (ex: recurso não encontrado, saldo insuficiente) tratada com status HTTP 4xx.
B) Um erro operacional é um defeito de hardware no servidor de banco de dados.
C) Um erro operacional ocorre apenas quando a internet cai.
D) Um erro operacional exige o reinício do servidor Node.js.
✅ Resposta Correta: A) Falha previsível de regra de negócio com status HTTP 4xx.
Justificativa: Erros operacionais são cenários conhecidos do sistema e devem retornar mensagens amigáveis ao cliente com status adequado.
3. No Express.js, quando um Controller captura um erro no bloco `catch (error)`, qual é a boa prática para encaminhá-lo ao Middleware Global de Erros?
A) Executar `console.log(error)` e ignorar a requisição.
B) Chamar a função `next(error)` repassando a exceção capturada.
C) Reiniciar a aplicação chamando `process.exit(1)`.
D) Chamar `res.send(error)` enviando a stack trace em texto puro.
✅ Resposta Correta: B) Chamar a função `next(error)`.
Justificativa: Passar o erro como argumento para `next(error)` instrui o Express a desviar a execução diretamente para o Middleware Global de Tratamento de Erros.
