01

Code Review em Equipe e Boas Práticas de Depuração

⏱️ Duração Estimada: 60 min

O Code Review (Revisão de Código) é uma prática essencial da engenharia de software colaborativa. Garante que todo código incorporado à branch principal do projeto atenda aos requisitos de qualidade, segurança, legibilidade e padrões arquiteturais estabelecidos.

1. Checklist Oficial de Code Review para o Projeto B2B

Categoria Item de Verificação Ação de Correção / Boa Prática
🔒 Segurança O arquivo .env está no .gitignore? Existem senhas/tokens em texto puro comitados? Remover segredos do código e garantir que senhas usam bcrypt e rotas privadas exigem JWT.
🧹 Limpeza Existem chamadas residuais de console.log() ou blocos de código comentados? Remover logs de rascunho. Manter apenas logs de auditoria estruturados no servidor.
⚠️ Resiliência Todas as funções assíncronas possuem bloco try/catch encaminhando o erro para next(error)? Garantir que exceções tratadas lançam AppError e requisições malformadas usam Zod.
🗄️ Banco de Dados As queries SQL utilizam parâmetros parametrizados ($1, $2) e liberam conexões do Pool? Eliminar concatenação direta de strings no SQL e assegurar o uso de client.release() em transações.

2. Técnicas e Ferramentas de Depuração (Debugging)

FRONT-END (Browser DevTools)

Utilização das abas Network (para inspecionar chamadas HTTP, payloads JSON, status codes e headers Authorization) e Console/Sources (para adicionar breakpoints na lógica do Fetch API).

BACK-END (Node Inspector & VS Code)

Uso do depurador integrado do VS Code (launch.json ou `--inspect`) para pausar a execução nos Controllers/Models, inspecionar variáveis de ambiente e rastrear a execução de queries SQL em tempo real.

💡 Dica de Ouro no DevTools: Se a sua requisição `fetch()` falhar com status 401 ou 403, verifique na aba Network -> Request Headers se o cabeçalho Authorization: Bearer <token> está de fato sendo transmitido com a palavra "Bearer " formatada corretamente.
02

Versionamento Colaborativo — Organização de Branches e Merge do Projeto

⏱️ Duração Estimada: 60 min

Trabalhar em equipes de desenvolvimento exige uma disciplina rigorosa no uso do **Git e GitHub**. Alterações diretas na branch principal (main) devem ser proibidas em favor da estratégia de Feature Branching e Pull Requests (PR).

1. O Fluxo de Trabalho com Feature Branches

1

Sincronização da Ramo Principal (`main`)

git checkout main seguido de git pull origin main para garantir que o repositório local possui as últimas atualizações aprovadas.

2

Criação da Branch de Funcionalidade

git checkout -b feature/autenticacao-jwt (cria e alterna para a nova branch isolada de trabalho).

3

Commits Atômicos e Envio ao GitHub

git add . $\rightarrow$ git commit -m "feat: implementado middleware de autenticacao jwt" $\rightarrow$ git push origin feature/autenticacao-jwt.

4

Abertura de Pull Request (PR) e Merge

No GitHub, abre-se o Pull Request solicitando a integração da `feature` para a `main`. Outro membro da equipe realiza o **Code Review** e aprova o **Merge**.

2. Resolução Prática de Conflitos de Merge (Git Merge Conflict)

Um Conflito de Merge ocorre quando dois desenvolvedores alteram as mesmas linhas de um mesmo arquivo em branches separadas. O Git interrompe a fusão e insere marcadores visuais no código: 

<<<<<<< HEAD (Sua alteração local na branch main)
router.get('/produtos', produtoController.listarProdutos);
=======
router.get('/produtos', autenticarToken, produtoController.listarProdutos);
>>>>>>> feature/autenticacao-jwt (Alteração vinda da branch a ser mesclada)
🛠️ Passo a Passo para Resolver o Conflito:
  1. Abra o arquivo conflitante no VS Code. Utilize as opções de resolução rápida (*Accept Current Change*, *Accept Incoming Change* ou *Accept Both*).
  2. Ajuste o código final garantindo que a sintaxe e as regras de negócio foram preservadas.
  3. Remova completamente os marcadores <<<<<<<, ======= e >>>>>>>.
  4. Salve o arquivo e finalize no terminal: git add . $\rightarrow$ git commit -m "fix: resolucao de conflito no roteador de produtos".
03

Desafio Prático — Consolidação e Apresentação do MVP Full Stack (Entrega Parcial 3)

⏱️ Duração Estimada: 60 min

As equipes realizarão a fusão final de todas as branches de funcionalidade no repositório remoto, executarão a bateria completa de testes de aceitação e apresentarão a versão funcional do **MVP Full Stack (Portal Comercial B2B)**.

1. Checklist de Validação da Entrega Parcial 3

1. Banco de Dados PostgreSQL

Tabelas relacionais criadas com chaves primárias/estrangeiras (`schema.sql`) e dados iniciais gravados via scripts de povoamento (`seeds.sql`).

2. API REST Node.js/Express

Estrutura MVC completa com rotas, controllers, models e DAO/Repository integrados via `pg.Pool` com transações atômicas.

3. Seguros & Resiliência

Senhas criptografadas com `bcrypt`, autenticação `JWT` em rotas privadas, validação de schemas com `Zod` e tratamento global de erros com `AppError`.

4. Interface Front-End Integrada

Telas em HTML/CSS/JS consumindo a API via `Fetch API`, salvando tokens no `localStorage` e atualizando a DOM dinamicamente.

2. Roteiro da Apresentação em Equipe (Pitch Técnico — 5 min)

A

Demonstração do Fluxo de Login B2B

Efetuar o login na interface visual com um usuário cadastrado, demonstrar o recebimento do Token JWT e sua gravação no `localStorage` do navegador.

B

Demonstração do CRUD e Validação de Borda

Tentar cadastrar um produto com dados inválidos para exibir o erro do `Zod` na tela e, em seguida, cadastrar um produto válido observando sua inserção no PostgreSQL e atualização na DOM.

C

Demonstração do Fechamento de Pedido Transacional

Realizar a criação de um pedido B2B com múltiplos itens, demonstrando no PostgreSQL a baixa automática de estoque e o encerramento da transação atômica.

Encerramento: Glossário da Aula + Quiz Final de Fixação

⏱️ Duração Estimada: 30 min

📚 Glossário Técnico da Aula

Code Review

Processo de revisão sistemática de código-fonte por pares para identificar bugs, vulnerabilidades e garantir padrões de arquitetura.

Feature Branching

Estratégia do Git onde cada nova funcionalidade é desenvolvida em uma branch isolada antes de ser mesclada na branch principal (`main`).

Git Merge Conflict

Situação em que o Git identifica edições concorrentes e incompatíveis nas mesmas linhas de um arquivo durante a fusão de ramos.

MVP (Minimum Viable Product)

Versão mais simples de um produto de software que contém os recursos essenciais para validar a solução junto aos usuários finais.

❓ Quiz Final de Fixação

1. Qual é a principal finalidade da prática de Code Review antes de realizar o merge de um Pull Request na branch `main`?
A) Bloquear o acesso dos desenvolvedores ao repositório do GitHub.
B) Assegurar a qualidade do código, identificar potenciais bugs ou brechas de segurança e garantir o cumprimento dos padrões arquiteturais da equipe.
C) Compilar o código JavaScript em linguagem Assembly.
D) Apagar as tabelas do PostgreSQL automaticamente.
✅ Resposta Correta: B) Assegurar a qualidade do código, identificar bugs e garantir padrões.
Justificativa: O Code Review atua como uma barreira de qualidade onde outros desenvolvedores inspecionam a alteração antes que ela impacte a aplicação principal.
2. Durante a resolução de um conflito de merge no Git, o que o desenvolvedor DEVE fazer com os marcadores `<<<<<<< HEAD`, `=======` e `>>>>>>> branch`?
A) Deixar os marcadores no código para que o Node.js os interprete.
B) Escolher o código correto desejado, consolidar as alterações e remover TODOS os marcadores do Git do arquivo antes de comitar.
C) Renomear o arquivo para `.env`.
D) Apagar a pasta `node_modules`.
✅ Resposta Correta: B) Consolidar as alterações e remover TODOS os marcadores antes de comitar.
Justificativa: Os marcadores são apenas sinalizadores temporários inseridos pelo Git. Mantê-los no arquivo gera erro de sintaxe no JavaScript.
3. Qual das alternativas representa uma boa prática de segurança que DEVE ser verificada durante o Code Review da Entrega Parcial 3?
A) Garantir que o arquivo `.env` contendo credenciais de banco e chaves secretas NÃO esteja incluído nos arquivos comitados do Git.
B) Salvar o token JWT diretamente em texto puro em uma variável global do CSS.
C) Desabilitar a criptografia `bcrypt` para acelerar os logins.
D) Permitir a inserção de SQL direto sem prepared statements.
✅ Resposta Correta: A) Garantir que o arquivo `.env` NÃO esteja comitado no Git.
Justificativa: O arquivo `.env` carrega informações sensíveis que jamais devem ir para repositórios públicos ou compartilhados.
