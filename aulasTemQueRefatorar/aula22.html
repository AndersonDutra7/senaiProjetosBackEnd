01

Configuração e Parametrização do Sistema para Produção

⏱️ Duração Estimada: 45 min

A transição de uma aplicação do ambiente de desenvolvimento local para o ambiente de **produção (Production)** exige o desacoplamento total entre o código-fonte e as configurações específicas de infraestrutura. Todas as credenciais, URLs de conexões de banco de dados e chaves secretas devem ser injetadas exclusivamente via Variáveis de Ambiente (Environment Variables).

1. Matriz Comparativa: Desenvolvimento vs Produção

Parâmetro Ambiente de Desenvolvimento (Dev) Ambiente de Produção (Prod)
NODE_ENV development (exibe stack traces de erros) production (otimiza desempenho e oculta erros internos)
🌐 Porta do Servidor Porta fixa estática (ex.: 3000) Porta dinâmica fornecida pela nuvem (process.env.PORT)
🗄️ Banco de Dados Instância local no localhost (sem SSL) Banco gerenciado em nuvem com conexão obrigatória via SSL/TLS
🔑 Segredos / JWT Chave simples de rascunho (ex.: "minhasenha123") Hash criptográfico de alta entropia (256 bits) injetado no PaaS
🛡️ Origem CORS Geralmente liberado (origin: "*") Restrito estritamente ao domínio do Front-End publicado

2. Configuração Dinâmica da Conexão PostgreSQL para Produção

No ambiente cloud, a biblioteca `pg` precisa reconhecer a string de conexão informada pelo provedor e habilitar a criptografia SSL obrigatória: 

// src/config/database.js
const { Pool } = require('pg');

const isProduction = process.env.NODE_ENV === 'production';

const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  ssl: isProduction ? { rejectUnauthorized: false } : false
});

module.exports = { pool };
⚠️ Regra de Ouro da Infraestrutura: O arquivo .env com valores reais de produção JAMAIS deve ser commitado no repositório Git. Utilize o arquivo .env.example como modelo documentado no repositório e cadastre os valores reais no painel de configurações (Environment Variables) do seu provedor de nuvem.
02

Elaboração do Plano de Implantação e Cronograma

⏱️ Duração Estimada: 45 min

O Plano de Implantação (Deployment Plan) é o documento normativo que organiza as atividades, a ordem cronológica dos procedimentos, as janelas de manutenção e a estratégia de recuperação em caso de falha (Rollback Strategy) durante o processo de liberação da aplicação.

Fases do Cronograma de Implantação

1

Fase Pre-Deploy (Preparação do Terreno)

Provisionamento do banco de dados relacional remoto no provedor Cloud, execução das DDLs (schema.sql), inserção dos dados semente e homologação das variáveis de ambiente no servidor.

2

Fase Deploy (Publicação do Código)

Conexão do repositório Git (branch `main`) ao serviço PaaS, execução do script de build (npm run build) e inicialização dos contêineres/processos do Node.js.

3

Fase Post-Deploy (Testes de Fumaça / Smoke Tests)

Validação dos endpoints críticos em produção (ex: chamada no endpoint `/healthcheck`, teste de login visual e verificação do tráfego HTTPS).

4

Plano de Contingência e Rollback

Em caso de falha crítica pós-implantação, aciona-se a reversão automática para a última tag Git estável ou a restauração do snapshot mais recente do banco de dados.

💡 O que é um Endpoint de Healthcheck? É uma rota leve criada na API (ex: GET /healthcheck) que apenas verifica a conectividade com o banco de dados e retorna status HTTP 200 com { status: "ok" }. Os servidores de hospedagem usam essa rota para saber se a aplicação está viva.
03

Boas Práticas de Segurança na Infraestrutura de Deploy

⏱️ Duração Estimada: 45 min

Publicar uma aplicação na internet expõe o servidor a escaneamentos automatizados e potenciais ataques maliciosos. Aplicar o princípio de Defense in Depth (Defesa em Profundidade) é fundamental para proteger os dados e os serviços.

Pilares Fundamentais do Hardening do Back-End

1. Criptografia HTTPS (TLS)

Todo o tráfego HTTP entre o navegador e o servidor Node.js deve ser criptografado via TLS (Porta 443 com certificado SSL), impedindo a interceptação de senhas e tokens por ataques Man-in-the-Middle.

2. Proteção de Cabeçalhos (Helmet.js)

O middleware helmet() oculta o cabeçalho X-Powered-By: Express e injeta diretivas de segurança contra ataques XSS, Clickjacking e Content Sniffing.

3. Limitação de Taxa (Rate Limiting)

O uso do express-rate-limit bloqueia ataques de força bruta no endpoint de login limitando a quantidade de requisições por IP em uma janela de tempo (ex.: máx 100 requisições / 15 min).

4. Menor Privilégio no Banco

A conta de banco usada pela aplicação Node.js em produção não deve ser o superusuário (`postgres`), mas sim um usuário com privilégios restritos às tabelas do schema da aplicação.

Exemplo de Aplicação das Camadas no Express

// src/app.js
const express = require('express');
const helmet = require('helmet');
const cors = require('cors');
const rateLimit = require('express-rate-limit');

const app = express();

// 1. Proteção de Cabeçalhos HTTP
app.use(helmet());

// 2. Restrição Estrita de CORS
app.use(cors({
  origin: process.env.CLIENT_URL || 'https://meusite.com',
  optionsSuccessStatus: 200
}));

// 3. Limite de Requisições contra Força Bruta
const limiter = rateLimit({
  windowMs: 15 * 60 * 1000, // 15 minutos
  max: 100, // Limite de 100 requisições por IP
  message: { error: 'Muitas requisições originadas deste IP, tente novamente mais tarde.' }
});

app.use('/api/', limiter);

Desafio Prático — Deploy da Aplicação Full Stack em Nuvem

⏱️ Duração Estimada: 45 min

As equipes deverão publicar a aplicação completa em ambiente de nuvem de produção/homologação (utilizando plataformas PaaS gratuitas como Render, Railway, Vercel ou Neon PostgreSQL), interligando todas as camadas em HTTPS.

Roteiro de Execução do Deploy em 4 Passos

A

1. Provisionamento do Banco PostgreSQL Remoto

Criar a instância de PostgreSQL em nuvem (ex.: Render ou Neon). Conectar via DBeaver/pgAdmin ou terminal e executar o script DDL schema.sql para criar a estrutura das tabelas em produção.

B

2. Deploy do Back-End Node.js (Web Service)

Conectar o repositório GitHub da equipe no PaaS. Configurar as variáveis de ambiente em nuvem: NODE_ENV=production, DATABASE_URL, JWT_SECRET e CLIENT_URL.

C

3. Deploy do Front-End e Vinculação

Publicar as telas HTML/CSS/JS (ex.: Vercel, Netlify ou Render Static) e atualizar a URL base das chamadas `fetch()` no arquivo JS para apontar para o domínio HTTPS público do Back-End recém-criado.

D

4. Execução de Smoke Tests e Validação

Acessar a URL pública da aplicação, efetuar login, realizar cadastros no banco remoto e confirmar o funcionamento ponta a ponta sem erros no console do navegador.

Checklist de Validação da Implantação

Camada Provedor / Recurso Status Esperado
🗄️ Banco de Dados PostgreSQL em Nuvem (Neon/Render) Tabelas criadas, conexão SSL ativa e dados gravados.
⚙️ Back-End API Node.js Web Service (Render/Railway) Servidor online com HTTPS e rota /healthcheck respondendo 200 OK.
💻 Front-End Hospedagem Estática (Vercel/Render) Interface visual acessível via HTTPS consumindo a API sem bloqueio de CORS.

Encerramento: Glossário da Aula + Quiz Final de Fixação

⏱️ Duração Estimada: 30 min

📚 Glossário Técnico da Aula

Deploy (Implantação)

Processo automatizado ou manual de transferência, compilação e execução de uma aplicação em um ambiente de hospedagem acessível.

PaaS (Platform as a Service)

Modelo de computação em nuvem em que o provedor gerencia a infraestrutura (servidores, rede, SO) e o desenvolvedor apenas publica o código da aplicação.

Helmet.js

Middleware essencial para Express que configura diversos cabeçalhos HTTP para defender a aplicação contra vulnerabilidades conhecidas da Web.

Rollback

Procedimento de contingência que reverte a aplicação implantada para uma versão anterior estável caso ocorram falhas imprevistas.

❓ Quiz Final de Fixação

1. Qual das alternativas representa uma ação CORRETA e obrigatória ao configurar as variáveis de ambiente para a publicação de uma API Node.js em ambiente de produção?
A) Commit do arquivo `.env` contendo as senhas reais do banco de dados no repositório público do GitHub.
B) Definir a variável `NODE_ENV=production` e cadastrar as senhas e chaves secretas diretamente nas configurações de Environment Variables do painel da plataforma cloud.
C) Apagar todas as variáveis de ambiente do código e escrever a string de conexão diretamente no arquivo `server.js`.
D) Desativar o uso de portas dinâmicas e forçar o uso da porta 3000 em todos os servidores da nuvem.
✅ Resposta Correta: B) Definir NODE_ENV=production e cadastrar as senhas no painel da nuvem.
Justificativa: As variáveis sensíveis devem ser injetadas pela plataforma de hospedagem em tempo de execução, mantendo o repositório seguro e limpo de segredos.
2. Qual é o papel principal da biblioteca `helmet` quando incorporada como middleware em uma aplicação web Express em produção?
A) Executar os testes de integração do banco de dados automaticamente a cada 5 minutos.
B) Configurar automaticamente diversos cabeçalhos HTTP de segurança para ocultar tecnologias internas e proteger contra ataques web como XSS e Clickjacking.
C) Criptografar as senhas das contas de usuários utilizando o algoritmo bcrypt.
D) Substituir a necessidade de utilizar o protocolo HTTPS/TLS no servidor.
✅ Resposta Correta: B) Configurar cabeçalhos HTTP de segurança e ocultar tecnologias internas do servidor.
Justificativa: O `helmet()` realiza o hardening dos cabeçalhos HTTP de forma simples e eficiente, elevando o nível de segurança padrão do Express.
3. O que define um procedimento de "Rollback" dentro de um Plano de Implantação de Software?
A) O processo de reescrever todo o código-fonte em outra linguagem de programação.
B) A ação emergencial de reverter o ambiente de produção para a versão anterior estável do código/banco de dados caso o novo deploy apresente erros graves.
C) A sincronização do arquivo `.gitignore` com o banco de dados PostgreSQL.
D) O bloqueio definitivo de todas as chamadas `fetch()` vindas do front-end.
✅ Resposta Correta: B) Ação emergencial de reverter o ambiente para a versão anterior estável caso o deploy falhe.
Justificativa: O Rollback é a estratégia de contingência que garante a disponibilidade do sistema minimizando o tempo de inatividade (downtime) em imprevistos.
