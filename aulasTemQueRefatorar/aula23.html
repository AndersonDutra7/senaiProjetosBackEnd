01

Manutenção Corretiva — Identificação e Correção de Falhas Pós-Implantação

⏱️ Duração Estimada: 45 min

A Manutenção Corretiva engloba as ações reativas executadas para diagnosticar e reparar falhas, bugs ou indisponibilidades identificadas após a publicação do software em produção. Para que a correção seja rápida e segura, a equipe deve contar com mecanismos eficientes de observabilidade e rastreamento de logs.

1. Diagnóstico de Incidentes Comuns em Produção

Tipo de Incidente Sintoma em Produção Ferramenta / Método de Diagnóstico Ação Corretiva Imediata
Vazamento de Conexão Requisições travam com timeout após determinado tempo de uso. Logs da aplicação com erro timeout exceeded when connecting to database. Garantir o uso obrigatório de try/finally com client.release() nas consultas ao PostgreSQL.
Unhandled Rejection Instância do Node.js cai ou reinicia de forma inesperada. Monitor de processos (ex.: PM2) ou logs da nuvem registrando erro não capturado.
Estouro de Memória O consumo de RAM cresce continuamente até causar crash do contêiner. Métricas do painel PaaS e heap dumps do Node.js Inspector. Otimizar queries SQL utilizando paginação (LIMIT/OFFSET) em vez de carregar milhões de linhas na memória.

2. Tratamento Global de Exceções Críticas no Node.js

Para impedir que exceções não tratadas derrubem silenciosamente o servidor em produção, a aplicação deve registrar ouvintes globais de processo para fins de log e encerramento gracioso (Graceful Shutdown): 

// src/server.js
const app = require('./app');

const PORT = process.env.PORT || 3000;

const server = app.listen(PORT, () => {
  console.log(`[INFO] Servidor rodando em modo ${process.env.NODE_ENV} na porta ${PORT}`);
});

// Captura de rejeições assíncronas não tratadas
process.on('unhandledRejection', (reason, promise) => {
  console.error('[CRÍTICO] Unhandled Rejection detectada:', reason);
  // Logar em serviço externo (ex: Sentry/Datadog) antes de encerrar
});

// Captura de exceções síncronas não tratadas
process.on('uncaughtException', (error) => {
  console.error('[FATAL] Uncaught Exception lançada:', error.message);
  server.close(() => process.exit(1));
});
⚠️ Análise de Causa Raiz (RCA — Root Cause Analysis): Resolver um bug em produção não se resume a aplicar um "patch" rápido. É obrigatório registrar o relatório Post-Mortem identificando por que a falha passou pelos testes, criar um novo teste automatizado que reproduza o bug e aplicar a correção definitiva na branch principal.
02

Manutenção Preventiva — Rotinas de Verificação e Roadmap de Atualização

⏱️ Duração Estimada: 45 min

Diferente das correções emergenciais, a Manutenção Preventiva e Adaptativa planeja ações contínuas para preservar a saúde do sistema, prevenir degradações de desempenho e manter o ecossistema atualizado contra vulnerabilidades de segurança conhecidas.

Os 4 Pilares da Manutenção Preventiva

1. AUDITORIA DE DEPENDÊNCIAS

Execução periódica de npm audit e atualizações de pacotes via ferramentas como Dependabot para corrigir brechas de segurança em bibliotecas terceirizadas.

2. MANUTENÇÃO DO BANCO

Rotinas de otimização no PostgreSQL: verificação do tamanho dos índices, limpeza de dados obsoletos, análise de fragmentação e validação diária de backups automáticos.

3. MONITORAMENTO DE RECURSOS

Acompanhamento de métricas de hardware (CPU, memória RAM, uso de disco) e tempo médio de resposta das rotas HTTP para prever a necessidade de escalonamento.

4. ROADMAP DE ATUALIZAÇÃO

Planejamento das versões do runtime Node.js (migração entre versões LTS) e atualização gradual do SGBD PostgreSQL e frameworks.

Exemplo de Estrutura de Roadmap de Atualização Tecnológica

Q1

Curto Prazo (Próximos 3 meses)

Atualização de patch das dependências do package.json, correção de alertas de segurança do npm audit e implementação de paginação nos endpoints do CRUD.

Q2

Médio Prazo (3 a 6 meses)

Atualização do runtime Node.js para a nova versão LTS estável, migração de rotas antigas para novos contratos REST e refatoração de consultas SQL complexas.

Q3

Longo Prazo (6 a 12 meses)

Implementação de camada de cache em memória (ex.: Redis) para consultas frequentes de leitura e transição do modelo monolítico para microsserviços se necessário.

03

Documentação Técnica do Processo de Implantação do Sistema

⏱️ Duração Estimada: 45 min

A Documentação de Implantação e Operação (Runbook) é o manual técnico indispensável que permite a qualquer desenvolvedor ou equipe de suporte provisionar, configurar, publicar, monitorar e manter a aplicação em funcionamento sem depender de conhecimento tácito.

Estrutura do Runbook de Implantação (`docs/DOCUMENTACAO_DE_IMPLANTACAO.md`)

1

Visão Geral da Arquitetura & Mapeamento de Serviços

Diagrama e descrição dos componentes (Front-End HTML/CSS/JS, Back-End Node.js/Express e Banco de Dados PostgreSQL), apontando as URLs públicas e domínios ativos.

2

Dicionário de Variáveis de Ambiente

Tabela detalhada especificando o nome de cada variável (ex.: DATABASE_URL, JWT_SECRET, PORT), o tipo de dado, a finalidade e um valor de exemplo fictício.

3

Guia Passo a Passo de Deploy e Inicialização

Comandos exatos do terminal necessários para clonar o repositório, instalar dependências (npm install), executar scripts DDL no PostgreSQL e iniciar o servidor em produção.

4

Procedimentos de Backup, Restauração e Contingência

Instruções detalhadas sobre como gerar dumps do PostgreSQL (pg_dump), como restaurar o banco de dados (pg_restore) e como executar o Rollback de versão no Git/PaaS.

💡 Boa Prática de Documentação: Mantenha toda a documentação técnica no próprio repositório Git do projeto utilizando arquivos Markdown (.md). Isso garante que o código e a documentação evoluam e sejam versionados juntos a cada Pull Request.

Encerramento: Glossário da Aula + Quiz Final de Fixação

⏱️ Duração Estimada: 30 min

📚 Glossário Técnico da Aula

Manutenção Corretiva

Intervenção realizada após a detecção de uma falha ou bug em ambiente de produção para reestabelecer o funcionamento normal do sistema.

Manutenção Preventiva

Ações planejadas de monitoramento, auditoria e atualização de código/banco de dados para evitar a ocorrência de futuras falhas ou gargalos.

Runbook

Documento de procedimentos operacionais padrão que orienta a equipe técnica na instalação, configuração, deploy, backup e resolução de falhas do sistema.

Root Cause Analysis (RCA)

Metodologia de investigação de incidentes focada em descobrir a causa primária de uma falha crítica para aplicar correções definitivas.

❓ Quiz Final de Fixação

1. Qual é a principal diferença conceitual entre a Manutenção Corretiva e a Manutenção Preventiva em um sistema de software publicado em produção?
A) A manutenção corretiva reescreve a aplicação em HTML, enquanto a preventiva altera o banco PostgreSQL.
B) A manutenção corretiva é reativa e repara bugs já ocorridos em produção, enquanto a preventiva é proativa e busca evitar falhas futuras por meio de auditorias e atualizações.
C) A manutenção preventiva só pode ser feita por clientes externos.
D) Não há diferença; ambas referem-se à mesma atividade de desligar o servidor de hospedagem.
✅ Resposta Correta: B) Corretiva é reativa para reparar bugs ocorridos; Preventiva é proativa para evitar falhas futuras.
Justificativa: A corretiva atua na solução imediata de problemas existentes, enquanto a preventiva atua na atualização contínua e mitigação de riscos.
2. Por que a inclusão de ouvintes globais para `unhandledRejection` e `uncaughtException` no Node.js é considerada uma boa prática de manutenção corretiva?
A) Porque impede que o banco de dados PostgreSQL execute comandos de exclusão `DROP TABLE`.
B) Porque permite capturar e registrar detalhadamente exceções não tratadas no log da aplicação antes que o processo caia de forma catastrófica e silenciosa.
C) Porque substitui a necessidade de utilizar variáveis de ambiente `.env`.
D) Porque compila automaticamente o código para JavaScript estático no navegador.
✅ Resposta Correta: B) Permite capturar e registrar detalhes de exceções não tratadas antes do encerramento do processo.
Justificativa: O tratamento global garante rastreabilidade e log adequado dos erros críticos, facilitando o diagnóstico rápido pela equipe de desenvolvimento.
3. Qual é a principal finalidade de manter uma Documentação de Implantação (Runbook) atualizada no repositório do projeto?
A) Permitir que qualquer membro da equipe consiga provisionar, configurar, publicar e operar a aplicação de forma padronizada e sem dependências individuais.
B) Aumentar o tamanho do repositório Git para acelerar o tempo de download no terminal.
C) Impedir o acesso de novos desenvolvedores ao código-fonte do sistema.
D) Ocultar as variáveis de ambiente dos servidores de produção.
✅ Resposta Correta: A) Permitir que qualquer membro consiga provisionar, configurar e operar a aplicação de forma padronizada.
Justificativa: O Runbook elimina o conhecimento isolado (silos de informação) e garante a continuidade operacional do software em longo prazo.
