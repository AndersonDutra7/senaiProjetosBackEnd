ITEM 01 Fácil
CAPACIDADE:
C1 – Correlacionar as demandas do cliente com as especificações técnicas do projeto.
Contexto:
Uma equipe de desenvolvimento backend para uma plataforma de e-commerce reuniu-se com o gerente de produto do cliente para alinhar as funcionalidades prioritárias do novo ciclo de entregas. O cliente expressou que a funcionalidade de recuperação de senha por e-mail é indispensável para a liberação da aplicação em produção, enquanto o módulo de recomendação de produtos baseado em inteligência artificial pode ser implementado em fases futuras sem impactar o lançamento inicial.
Comando:
Considerando a aplicação da técnica de priorização MoSCoW para correlacionar corretamente as demandas apresentadas pelo cliente ao backlog da aplicação, qual alternativa descreve a classificação adequada dessas funcionalidades?
Alternativas:
a) A funcionalidade de recuperação de senha deve ser classificada como Could Have por ser uma solicitação frequente de usuários finais em sistemas legados, enquanto o módulo de recomendação por inteligência artificial é classificado como Must Have por representar o grande diferencial competitivo de mercado do produto contratado.
b) A funcionalidade de recuperação de senha deve ser enquadrada como Should Have para garantir que os testes de carga sejam finalizados antes de sua publicação, e o módulo de recomendação deve ser rotulado como Won't Have nesta versão para reduzir custos.
c) O módulo de recomendação deve ser classificado como Must Have para garantir a monetização imediata da plataforma, e a recuperação de senha deve ser alocada como Could Have.
d) A recuperação de senha é um requisito Must Have, enquanto o sistema de recomendação classifica-se como Could Have.
ITEM 02 Média
CAPACIDADE:
C1 – Correlacionar as demandas do cliente com as especificações técnicas do projeto.
Contexto:
Durante o levantamento de regras de negócio de um sistema de gestão financeira corporativa, o cliente solicitou que o sistema bloqueie automaticamente a emissão de notas fiscais caso a empresa contratante esteja inadimplente há mais de 30 dias. Além disso, exigiu que a liberação da funcionalidade ocorra de forma imediata assim que a confirmação do pagamento for recebida via notificação assíncrona de um gateway bancário.
Comando:
Ao correlacionar essa demanda do cliente com o projeto da arquitetura backend em Node.js, qual alternativa descreve o fluxo técnico adequado para atender a esse requisito de negócio?
Alternativas:
a) O endpoint de emissão de nota fiscal deve consultar diretamente a base de dados em memória do cliente no front-end para determinar se a empresa possui débitos pendentes, dispensando a validação das regras de negócio na camada backend de serviços da aplicação Node.js para otimizar o tempo de resposta e consumo de CPU.
b) O endpoint de emissão deve consultar a camada de serviço do backend para validar o status de adimplência do cliente antes de gerar a nota, e o endpoint do webhook deve atualizar o status financeiro do cliente no banco de dados assim que receber a notificação do gateway bancário.
c) O sistema deve criar um agendamento assíncrono para emitir todas as notas fiscais no final do dia, sem realizar validações de pendências financeiras no momento do envio da requisição HTTP pelo usuário no front-end.
d) O webhook de pagamento deve reescrever o código-fonte da rota de emissão no servidor Node.js a cada confirmação bancária recebida.

Entre as declarações registradas na documentação, destacam-se duas: "O sistema deve permitir que o usuário autentique-se via Single Sign-On (SSO) do Google" e "A API deve responder a 95% das requisições de busca em tempo inferior a 200 milissegundos".

Com base na classificação formal aplicada no levantamento de requisitos de software, qual alternativa diferencia corretamente a natureza dessas duas especificações?

b) Ambas as declarações representam requisitos funcionais da aplicação backend, pois ambas descrevem comportamentos que dependem diretamente de ações manuais do usuário final durante a navegação na plataforma.
c) O login via Google é um Requisito Funcional, pois descreve uma ação que o sistema deve realizar, enquanto o tempo de resposta inferior a 200ms é um Requisito Não Funcional, pois especifica uma qualidade de desempenho.
d) O tempo de resposta de 200ms é um Requisito Funcional básico, e a autenticação externa é um Requisito Não Funcional opcional.

ITEM 06 Difícil
CAPACIDADE:
C2 – Aplicar técnicas de levantamento de requisitos
Contexto:
Uma equipe de engenharia foi encarregada de projetar uma API para processar pagamentos simultâneos em eventos de alta demanda. Durante o levantamento de requisitos não funcionais de desempenho para a infraestrutura Node.js, observou-se que operações bloqueantes de entrada e saída (I/O) no sistema de arquivos ou no banco de dados poderiam congelar o Event Loop, degradando severamente a capacidade de resposta da API.
Comando:
Considerando a análise desse requisito não funcional e a arquitetura single-threaded do Node.js, qual decisão técnica atende de forma mais adequada às exigências de concorrência e desempenho?
Alternativas:
a) Substituir o uso de chamadas assíncronas no Node.js por rotinas síncronas com fs.readFileSync e operações bloqueantes de leitura de banco de dados, garantindo que cada requisição HTTP execute isoladamente do início ao fim sem intercalação de eventos na memória do servidor.
b) Priorizar chamadas não bloqueantes baseadas em Promises e async/await, delegando operações pesadas de I/O ou processamento intensivo de CPU para workers dedicados ou filas assíncronas, preservando o Event Loop livre para responder a novas conexões.
c) Criar uma nova thread do sistema operacional de forma síncrona a cada nova requisição HTTP recebida, ignorando o modelo de Event Loop de thread única do Node.js para simular um servidor tradicional multithread.
d) Desativar o mecanismo de log de erros no servidor para evitar que o Event Loop seja suspenso durante requisições simultâneas.

C4- Aplicar técnicas de modelagem de dados
Contexto:
Uma equipe de engenharia backend em Node.js está modelando a base de dados de uma plataforma de e-commerce. Durante o levantamento de entidades, identificou-se que um Cliente pode realizar múltiplos Pedidos, mas cada Pedido pertence a apenas um único Cliente.
Comando:
Para garantir a correta representação dessa regra de negócio no modelo relacional do sistema, qual estratégia de modelagem de dados deve ser adotada pela equipe?
Alternativas:
a) A equipe deve criar uma terceira tabela intermediária contendo as chaves primárias das duas entidades, pois relacionamentos em sistemas transacionais distribuídos exigem a transformação obrigatória de qualquer vínculo em uma estrutura associativa independente para evitar acoplamento no banco.
b) A equipe deve replicar todos os campos da tabela de Clientes diretamente dentro da tabela de Pedidos, eliminando a necessidade de relacionamentos relacionais e tratando o banco de dados como um repositório chave-valor não estruturado.
c) A equipe deve definir uma relação de 1:N (um para muitos), inserindo a chave primária de Cliente como chave estrangeira na tabela de Pedidos para mapear o vínculo.
d) A equipe deve criar uma relação N:N vinculando diretamente as tabelas sem o uso de chaves estrangeiras.
ITEM 08 Média
CAPACIDADE:
C4- Aplicar técnicas de modelagem de dados
Contexto:
Ao analisar a tabela de transações bancárias de uma fintech desenvolvida em Node.js, o arquiteto de software notou que a tabela continha o ID da transação, o valor, a data, o ID do cliente, o nome do cliente, o CPF do cliente e o endereço do cliente. Toda vez que um cliente realizava uma nova transação, seus dados pessoais e de endereço eram duplicados na tabela de transações.
Comando:
Considerando as boas práticas de modelagem relacional para eliminar anomalias de atualização e redundâncias, qual procedimento de normalização deve ser aplicado a essa estrutura?
Alternativas:
a) Aplicar a Terceira Forma Normal (3FN), separando os dados cadastrais do cliente em uma tabela própria e mantendo na tabela de transações apenas a chave estrangeira do cliente, garantindo que atributos não chave dependam exclusivamente da chave primária.
b) Aplicar a Primeira Forma Normal (1FN), convertendo os dados do cliente em coleções multivaloradas do tipo matriz dentro de uma única coluna da tabela de transações, mantendo a redundância estrutural no banco.
c) Desnormalizar a tabela para a Forma Normal Zero, unificando os dados das transações com logs de auditoria para acelerar as consultas na API REST.
d) Criar índices secundários em todas as colunas redundantes para mitigar as falhas de integridade durante as gravações.
ITEM 09 Difícil
CAPACIDADE:
C4- Aplicar técnicas de modelagem de dados
Contexto:
Uma startup de entrega de encomendas está reestruturando sua API de rastreamento em Node.js. O sistema precisa registrar o histórico de rotas e eventos de localização em tempo real, onde cada pacote possui dezenas de atualizações de status por minuto com campos altamente dinâmicos (coordenadas GPS, temperatura do baú, velocidade, fotos de comprovação de entrega). A equipe avalia se deve modelar esses dados em um banco relacional (PostgreSQL) com relacionamentos complexos ou em um banco NoSQL orientado a documentos (MongoDB).
Comando:
Analisando as características técnicas e a volumetria dinâmica do cenário, qual alternativa justifica corretamente a escolha do modelo de dados mais adequado?
Alternativas:
a) O modelo relacional é o mais indicado pois impede alterações na estrutura de dados em tempo de execução, obrigando que todas as coordenadas e metadados de rastreamento sigam estritamente o mesmo esquema de tabela fixo sem comprometer a latência da API.
b) O modelo relacional com tabela única unificada é superior pois elimina a necessidade de chaves primárias e índices, garantindo throughput de gravação ilimitado para dados estruturados complexos.
c) O modelo NoSQL chave-valor é indispensável pois permite realizar junções relacionais de alta complexidade (JOINs) entre entidades heterogêneas sem consumir memória do servidor Node.js.
d) O modelo NoSQL orientado a documentos é ideal devido ao esquema flexível e alta performance em gravações de dados semiestruturados e voláteis.

c) Gravar os registros em arquivos de log em disco rígido locais no servidor Node.js antes de enviar as consultas SQL isoladas para o banco de dados.

ITEM 15 Média
CAPACIDADE:
C5- Seguir recomendações técnicas na aplicação da linguagem de definição e manipulação de dados
Contexto:
Em uma API de relatórios para um marketplace com milhões de vendas registradas, as consultas de busca por período e ID do vendedor estavam demorando vários segundos para responder. O analista de banco de dados sugeriu criar um índice composto na tabela de vendas utilizando a linguagem de definição de dados (DDL) para otimizar as leituras frequentes.
Comando:
Considerando os impactos de desempenho na definição e manipulação de dados, qual recomendação técnica deve ser avaliada antes de criar múltiplos índices na tabela?
Alternativas:
a) Embora os índices acelerem significativamente as consultas de leitura (SELECT), eles geram custo adicional nas operações de escrita e manipulação de dados (INSERT, UPDATE e DELETE), pois o SGBD precisa atualizar a estrutura do índice a cada alteração na tabela.
b) Os índices criados via DDL bloqueiam permanentemente as operações de leitura na tabela durante a execução de transações DML, tornando o banco inacessível para os clientes do sistema.
c) A criação de índices aumenta o tempo de resposta das consultas SELECT, pois obriga o motor do banco a varrer todas as páginas de dados sequencialmente.
d) Os índices substituem a necessidade de chaves primárias e estrangeiras nas tabelas relacionais.
ITEM 16 Difícil
CAPACIDADE:
C5- Seguir recomendações técnicas na aplicação da linguagem de definição e manipulação de dados
Contexto:
Uma equipe backend refatorou um microsserviço em Node.js substituindo a escrita manual de queries SQL puras por um ORM (Object-Relational Mapping). Em uma das rotas de listagem de produtos com suas respectivas categorias, a API passou a apresentar queda severa de performance, executando 1 consulta para buscar 100 produtos e mais 100 consultas individuais para buscar a categoria de cada produto (problema do N+1 queries).
Comando:
Qual recomendação técnica de manipulação e consulta de dados deve ser aplicada para resolver o gargalo de desempenho gerado pelo uso do ORM?
Alternativas:
a) Configurar a ORM para executar as 100 consultas individuais dentro de um laço de repetição assíncrono (async/await) na aplicação Node.js, aumentando a quantidade de conexões concorrentes no pool do banco de dados relacional para distribuir a carga de processamento.
b) Substituir o banco relacional por um repositório NoSQL de arquivos texto sem índices, eliminando a camada de persistência para que a aplicação processe os dados diretamente em memória RAM.
c) Ajustar o carregamento dos dados para utilizar junções (Eager Loading / JOIN) na mesma consulta, reduzindo a busca a uma única instrução SQL.
d) Adicionar cláusulas de ORDER BY DESC em todas as subconsultas geradas automaticamente pela ORM.

Comando:
Qual procedimento técnico adequado deve ser adotado pelo desenvolvedor para resolver esse conflito e manter o repositório consistente?

a) Abrir o arquivo routes.js, analisar as marcações de conflito (<<<<<<<, =======, >>>>>>>), decidir junto com a equipe qual código deve prevalecer, remover as marcações manuais, salvar o arquivo, adicioná-lo à staging area (git add) e finalizar a fusão com um novo commit.

ITEM 20 Difícil
CAPACIDADE:
C6- Aplicar técnicas de versionamento de software
Contexto:
Um time de engenharia de software prepara a liberação da versão 2.4.1 de um microsserviço Node.js para o ambiente de produção. Para garantir a rastreabilidade das entregas na esteira de CI/CD, a equipe utiliza a especificação Semantic Versioning (SemVer - MAJOR.MINOR.PATCH) e precisa marcar o commit exato da liberação no histórico do Git.
Comando:
Considerando a regra do Semantic Versioning e as boas práticas de versionamento, o que representa a alteração do número PATCH (de 2.4.0 para 2.4.1) e qual comando Git fixa essa versão no repositório?
Alternativas:
a) A alteração no número PATCH indica a introdução de uma nova funcionalidade incompatível com as versões anteriores da API, e o comando utilizado para registrar essa versão é o git commit -m "v2.4.1".
b) O incremento do PATCH indica a reestruturação completa da arquitetura do banco de dados, e o comando correto para publicar essa mudança no repositório remoto é git branch v2.4.1.
c) O PATCH indica correções de bugs retrocompatíveis sem adição de novas funcionalidades, e o comando git tag -a v2.4.1 -m "Release v2.4.1" cria a anotação do marco no Git.
d) O PATCH indica a adição de funcionalidades compatíveis, e o comando é git checkout -b v2.4.1.
