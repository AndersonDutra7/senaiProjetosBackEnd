ITEM 01 Fácil
CAPACIDADE:
C1- Considerar o escopo do projeto na escolha dos protocolos de comunicação de sistemas web
Contexto:
Uma equipe de desenvolvimento backend em Node.js está projetando um sistema de atendimento ao cliente em tempo real para um aplicativo de telemedicina. O requisito principal do sistema é permitir a troca instantânea de mensagens bidirecionais entre o paciente e o médico sem a necessidade de o cliente realizar sucessivas requisições de sondagem (polling) ao servidor.
Comando:
Para atender ao requisito de comunicação bidirecional contínua em tempo real de forma eficiente, qual protocolo de comunicação web deve ser selecionado pela equipe?
Alternativas:
a) O protocolo HTTP/1.1 operando no modo stateless padrão, pois obriga a abertura e o fechamento de uma nova conexão TCP a cada mensagem enviada pelo usuário, garantindo a máxima segurança no tráfego de dados sensíveis de saúde sem consumir recursos permanentes de memória no servidor Node.js.
b) O protocolo SOAP baseado no formato XML, pois fornece criptografia nativa no nível de transporte de mensagens assíncronas e gerencia a persistência de estados atômicos entre o cliente web e o backend da aplicação.
c) O protocolo WebSockets, pois estabelece uma conexão full-duplex permanente sobre uma única tomada TCP, permitindo o envio de dados em tempo real com baixa latência.
d) O protocolo FTP, pois é otimizado para o envio assíncrono de pacotes de dados textuais.

b) REST utilizando HTTP/1.1 com payloads em formato XML estritamente validados por esquemas XSD, pois garante maior velocidade de navegação na rede interna e suporte nativo em navegadores web.
c) WebSockets com payloads serializados em formato YAML, pois converte automaticamente chamadas síncronas em eventos assíncronos desacoplados.
d) GraphQL sobre HTTP/1.0 enviando requisições GET com dados codificados em Base64.

ITEM 21 Difícil

C7- Aplicar as configurações e parametrizações do sistema
Contexto:
Uma API financeira em Node.js/Express sofreu lentidão devido a um volume anormal de requisições automatizadas em um curto intervalo de tempo. Para proteger o servidor contra indisponibilidade e ataques de força bruta, a equipe configurou um limitador de taxa de requisições (rate-limiting).
📁 rate_limit.js 
const rateLimit = require('express-rate-limit');

const limiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  max: 100,
  message: 'Muitas requisições originadas deste IP.'
});

app.use(limiter);
Comando:
Como essa parametrização de infraestrutura protege o sistema web contra exaustão de recursos?
Alternativas:
a) A parametrização de rate limiting limita a quantidade de requisições por IP em um determinado intervalo de tempo, bloqueando abusos e requisições maliciosas com o código HTTP 429 Too Many Requests antes que afetem o processamento do servidor backend.
b) O rate limiting duplica o número de threads do servidor Node.js para cada nova requisição recebida, garantindo que ataques DDoS sejam processados sem aumento de latência.
c) A configuração altera o banco de dados de relacional para NoSQL automaticamente sempre que a CPU atingir 100% de uso.
d) O middleware deleta os logs do sistema operacional para liberar espaço no disco rígido.
