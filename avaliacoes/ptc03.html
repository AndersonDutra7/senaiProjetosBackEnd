CONTEXTO DA SITUAÇÃO DE APRENDIZAGEM

A AutoVision é uma plataforma web de anúncios de veículos usados que conecta vendedores e compradores por meio de uma API REST desenvolvida em Node.js com Express e banco de dados PostgreSQL. A aplicação possui endpoints para listagem e busca de anúncios, autenticação de usuários, registro de interesse em veículos, gerenciamento de perfis e publicação de novos anúncios com upload de imagem. A equipe responsável pelo desenvolvimento concluiu a implementação das rotas principais e agora precisa garantir a qualidade, a segurança e a confiabilidade da plataforma antes de disponibilizá-la para os usuários. Para isso, é necessário elaborar e executar um plano de testes estruturado, identificar e corrigir vulnerabilidades na camada de comunicação e assegurar que o banco de dados opere de forma segura e isolada.

COMANDO DA SITUAÇÃO DE APRENDIZAGEM

A equipe deverá atuar como um time de Quality Assurance (QA) e Segurança responsável por validar a plataforma AutoVision antes do seu lançamento.

Vocês deverão elaborar e executar um Plano de Testes cobrindo os cenários funcionais e de exceção das rotas da API (GET /api/anuncios, POST /api/login, POST /api/interesses/:id, POST /api/anuncios e DELETE /api/anuncios/:id), implementar mecanismos de segurança na camada HTTP (validação de entradas, proteção de credenciais e controle de acesso) e documentar e corrigir as falhas identificadas durante o processo, registrando o ciclo completo de resolução de problemas.

Ao final, a equipe entregará os artefatos distribuídos nas seções abaixo, todos versionados no repositório do projeto.

DESAFIO — ENTREGÁVEIS DETALHADOS

Espera-se que a plataforma AutoVision seja entregue com qualidade e segurança comprovadas, demonstrando na prática: a elaboração e execução de um plano de testes estruturado, a implementação das camadas de segurança HTTP, a identificação e correção de vulnerabilidades e a configuração segura do banco de dados. Os artefatos estão detalhados nas seções abaixo.

SEÇÃO 01 — Plano de Testes e Relatório de Execução
Item Artefato Descrição
1.1 Documento do Plano de Testes Elaborar o Plano de Testes da AutoVision contendo: escopo dos testes (endpoints cobertos), responsabilidades da equipe, ambiente e ferramentas utilizadas, critérios de entrada e saída, e tabela de casos de teste para cada rota da API (GET /api/anuncios com e sem filtro, POST /api/login com credenciais válidas e inválidas, POST /api/interesses/:id com campos faltantes, POST /api/anuncios sem imagem, DELETE /api/anuncios/:id).
1.2 Scripts de Teste e Relatório de Execução Implementar os testes automatizados (unitários e/ou de integração) utilizando framework adequado (ex.: Jest + Supertest) cobrindo os cenários definidos no plano. Entregar o relatório consolidado com: status de cada caso de teste (passou/falhou), métricas de cobertura e evidências de execução (print do terminal ou arquivo de log).
SEÇÃO 02 — Camada de Segurança e Middlewares de Proteção
Item Artefato Descrição
2.1 Validação e Sanitização de Dados Implementar validação dos campos obrigatórios e sanitização das entradas em todos os endpoints, prevenindo injeção SQL (verificar uso de queries parametrizadas), XSS e envio de payloads malformados. Documentar as regras de validação aplicadas por endpoint.
2.2 Cabeçalhos de Segurança HTTP e CORS Configurar cabeçalhos de segurança HTTP (via biblioteca Helmet ou equivalente) incluindo Content-Security-Policy, X-Content-Type-Options e X-Frame-Options. Definir e documentar a política de CORS da aplicação.
2.3 Tratamento Centralizado de Erros Implementar middleware de tratamento centralizado de erros garantindo que as respostas de erro não exponham detalhes internos da aplicação (stack traces, senhas, estrutura do banco) e retornem mensagens padronizadas com códigos HTTP apropriados.
SEÇÃO 03 — Checklist de Vulnerabilidades e Relatório de Resiliência
Item Artefato Descrição
3.1 Checklist de Segurança (OWASP Simplificado) Preencher o Checklist de Segurança da Informação verificando os principais pontos de vulnerabilidade da AutoVision: exposição de dados sensíveis (senha em texto puro no banco), ausência de autenticação em endpoints críticos, falhas de autorização (qualquer usuário pode excluir qualquer anúncio), ausência de rate limiting e validação de tipo de arquivo no upload.
3.2 Relatório de Resiliência e Ciclo de Correção Elaborar o Relatório de Resiliência documentando para cada falha identificada: (1) hipótese formulada, (2) forma de testagem da hipótese, (3) solução implementada e (4) validação do resultado — evidenciando o ciclo completo de resolução de problemas.
SEÇÃO 04 — Configuração Segura do Banco de Dados
Item Artefato Descrição
4.1 Ambiente de Testes Isolado (PostgreSQL) Configurar um banco de dados PostgreSQL dedicado para o ambiente de testes, separado do banco de desenvolvimento, com script de criação e população de dados fictícios (seed) para execução dos testes automatizados.
4.2 Controle de Acesso (DCL) e Gestão de Credenciais Aplicar DCL (Data Control Language) criando um usuário de banco de dados com permissões mínimas necessárias para a aplicação (sem acesso de superusuário). Documentar o processo de migração das credenciais hardcoded do server.js para variáveis de ambiente (.env), entregando o modelo .env.example.
Formato das entregas: Os artefatos documentais (Plano de Testes, Relatório de Execução, Checklist de Segurança e Relatório de Resiliência) devem ser entregues em formato PDF. Os scripts de testes automatizados, middlewares implementados e arquivos de configuração do banco de dados deverão ser versionados no Repositório Git do projeto com evidências visuais de execução (prints ou logs do terminal).
